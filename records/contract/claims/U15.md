## K-296-2 · C:296 · example

**Pass.** examples-request
**Claim.** "…but can be removed after observed absence"
**Mechanism.** `runner remove` (`cmd_runner_remove`) takes the registry lock, loads the registry and calls `remove_record` with `NativeCleanup`. `remove_record` never reads `record.contract`. In order:
1. If the record is in `runners`, it is moved to `pending_cleanup` with a start time and the registry is saved; this save must succeed before any launchd or plist action.
2. `system.location(record)` gives the plist path and launchd domain. The service (`launchctl print`) and the plist are observed, and ownership is computed for each: `service_ownership` is `Owned` only when the service is present and its reported executable path equals the record's; `plist_ownership` is `Owned` only when the plist is a regular file whose `Label`, `ProgramArguments`, `MachServices` and `XPC_SERVICE_PATH` match the record and, when the record carries `ownership`, whose owner uid and SHA-256 match. A "before" observation is appended to the cleanup record.
3. If the service is not absent and `--skip-bootout` was not given: `launchctl bootout` only when service ownership is `Owned`; otherwise a warning "bootout refused".
4. If the plist is not absent: it is re-inspected immediately before unlinking and removed only if still `Owned`; otherwise a warning.
5. `service_after_bootout` re-reads the service at a poll interval within a wait budget; the plist is observed again; an "after" observation is appended.
6. `complete = cleanup_complete(service_after, plist_after) && warnings.is_empty()`, where `cleanup_complete` requires both presences to be `Absent` (an `Unknown` observation is not absence). Only when complete is the `pending_cleanup` entry dropped. Otherwise it is retained with the warning `service/plist absence is not confirmed; cleanup record retained`, and the report has `cleanup_retained: true`. A failed final save also forces retention.
A later `runner remove` finds the entry in `pending_cleanup` and repeats from step 2. The controller decides throughout; the rule exists once, in Rust.
