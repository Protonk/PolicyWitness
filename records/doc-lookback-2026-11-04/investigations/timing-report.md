## Findings

**T1 — confirmed clock wording mismatch (C0-3).** LIMITS lines 99–100 and 112 say nominal readiness, publication and validator grace waits. `ActorSession` readiness/grace, `runCWorker` publication and `runValidator` grace instantiate `HostWaitClock`: elapsed `CLOCK_MONOTONIC`, bounded sleeps, charged polling costs and sticky fault fallback to the remaining nominal sleeps. ARCHITECTURE 355–358 and LIMITS 273–274/286/426–435 describe this correctly. `CWorkerClockTests` separately assert oversleep, irregular costs, interruption, regression, exclusion and last-sleep accounting; retained core log lines 474–487 records their passes. Keep “nominal” for removal's summed sleeps and the unenforced release margin. This is a documentation conflict, not evidence of a timer defect. Change owning `docs/limits.json` rows and regenerate LIMITS/guide; no runtime change needed unless intended semantics differ.

**T2 — confirmed actor scope/control omissions (L-Q5/Q6).** `runActors` uses one global collectionRemainingNs initialized to min(30000, override), floored at 1; the total override therefore applies to actors although actor_collection_allowance says Fixed. There are not two collection pools. The actor scheduler uses one 120000 ms schedule clock, excludes synchronous collection, and does not invoke legacy `runCWorker`'s separate sentinel loop. Generic worker_sentinel_wait should be explicitly legacy; its worker_timeout_ms override is max(50,v), uncapped above, and does not change actor execution allowance. Generic policy/readiness waits apply to actors but are capped by the remaining setup allowance. Validator I/O proposal has its own max(50,v) override, but aggregate remaining can reduce the effective deadline below 50. Actor setup clock actually starts before authority-region preparation, before the first launch; LIMITS 101's “from the first actor launch” omits charged work. These are implementation-source findings; legacy PhaseProtocolTests:303's 500 ms aggregate control establishes exhaustion/continued attempts, not an actor default-duration boundary. Remedy: explicitly map form, shared pools, starts and controls in owning limits rows; implementation unification is an alternative if duplicated orchestration accounting should become one maintained contract, requiring both-form controls.

**T3 — confirmed sampled-cutoff qualification needed (A-F4, L-Q4, M08).** LIMITS 106's “A worker that reaches the cutoff publishes a timing failure and exits” is too unconditional. `ActorScheduler.init` computes one raw continuous cutoff before setup. Worker checks an already-past cutoff before policy reading, then samples it in activation, release and exchange waits. Neither `run_attempt`'s ordinary native calls nor exec collection/reap checks this cutoff. No asynchronous worker cutoff timer was found. A blocked native call can outlast it; host execution expiry can request termination but successful termination leads to a blocking host final wait. `wait_exchange` checks an already-visible acknowledgement before sampling expiry, unlike `wait_for_proceed`'s expiry-before-release order. The host recipient loop has its own monotonic allowance capped by remaining execution, not a direct continuous cutoff comparison. Do not convert any of these into a wall-clock guarantee. Local SDK `usr/include/mach/mach_time.h:59–62` documents continuous time advancing during sleep; actual sleep was not experimentally established here. Remedy options: document sampled enforcement and nonpreemptible/cleanup exclusions, or design an explicit hard lifecycle contract and implementation with separate evidence for failure to terminate. Merely renaming a budget cannot provide that contract.

**T4 — confirmed actor exec-accounting omission.** LIMITS 114/288 describes excluding acknowledged release waits only. `wait_for_activation` also adds the parked interval to each actor worker's plan_deadline exactly when activation is accepted. Thus exec_attempt_budget is 115000 ms per worker/actor from its own origin, including its setup/intervening work, excluding accepted activation waits as well as acknowledged release waits; it is not the global actor execution pool. The arithmetic margin below 120000 is configuration, not shared epochs. Add actor applicability/exclusion in limits input and its architecture/worker consumers. Source provides the changed exclusion; retained short-budget exec remainder control establishes its own legacy scenario only, not a new actor-exclusion boundary experiment.

**T5 — confirmed measurement-scope limitation, not failed qualification.** `check_actor_timing_qualification.py:intervals` measures exchange only through host transfer.recipient_wait. It does not measure worker custody-ack or transfer-answer intervals. Its total is setup_wait.elapsed + execution_wait.elapsed, excluding `finish()` cleanup and the small interval from cutoff calculation to setup clock start. Host arrival-to-release is also a publication/scheduling proxy for worker release wait, not the worker's own sampled interval. Therefore README's “lifetime total” and an inference that the quarter-margin covers every exchange/lifetime interval are stronger than the measurement. The documented finite-workload qualification itself is supported: three rounds of 1/3/8 actors, one 256-action/16-phase workload, and two authority shapes. Retained report says qualified=true; largest setup 181 ms, charged execution 39 ms, aggregate collection 33 ms, release proxy 3 ms, recipient exchange 1 ms, setup+execution total 235 ms. It establishes these particular normal workloads on recorded Apple M5/macOS 26.7.1 AC-powered equipment. It establishes neither production timeout duration nor arbitrary maximal plans. Remedies: label the proxies and limited measured intervals accurately, or add instrumentation and independent assertions for the intended broader measurement. Test owner is witness_contract checker/README; affected limits control/coverage claims are all six actor timing rows. No new run is needed to establish the scope mismatch.

**T6 — platform claim needs narrowing.** The generated plist sets ThrottleInterval=1 second. Local `/usr/share/man/man5/launchd.plist.5:409` supports that this overrides a default throttle policy of no more than one spawn per ten seconds. It does not establish LIMITS 118's deterministic claim that a pending request is served after precisely the remainder, nor a general request-delivery guarantee. Retain configured launch pacing; qualify observed service timing if backed by an actual trace. Source/tests establish the plist value, not every launchd scheduling behavior. A documentation remedy belongs to byoxpc_throttle_interval in limits.json; a stronger intended guarantee requires a suitable primary platform contract, not a faster loop test.

**T7 — declaration scope clarification supported.** extension_issuer_wait is 5000 ms from successful helper spawn before worker creation; target preparation and spawn precede it, termination/reap follow it and may overrun. Actor dispatch returns through runActors before constructing ExtensionSession; actor issue actions do not get this helper budget. Add explicit declaration-form applicability. sysctl_read_bytes needs no change: one non-null 4096-byte destination, no sizing/retry, discarded bytes/returned length; native failure alone cannot attribute capacity insufficiency.
