## K-165-1 · C:165 · evidence

**Pass.** gates-lifecycle-profile
**Claim.** "Lifecycle claims depend on native progress, collection and termination observations."
**Mechanism.** Two hand-written implementations plus a Python reader that was not opened.
1. Producer (Swift host): `resolveDisposition` builds one `PWDispositionRecord` per worker. Each question is a `PWDispositionClaim` with a `state` (`supported`, `unresolved`, `inapplicable`, `conflicting`) and a `basis` list of tokens naming the raw facts used. `final_status` is computed from `out.reaped`, `out.exitCode`, `out.termSignal` (termination). `collection_basis` comes from `out.collectionBasis` (collection). `progress_association` comes from `workerEvidence.progress` (progress). Per step, `step_boundary_reached` and `step_result_published` are computed from the progress position, the slot state and `terminal = collectionBasis == "after_confirmed_reap" && reaped == true`.
2. Reader (Rust controller): `validate_lifecycle` calls `check_claim` for every run and step question. A `supported` claim must have an answer, a nonempty basis, pass `sufficient(q, c)` (not opened) and have every basis token resolve against the subprocess record. The function then recomputes the relationships from the raw fields (`reaped`, `exit_code`, `term_signal`, `collection_basis`, progress word, slots) and compares. `project` decides the public `process_disposition`.
**When it does not hold.** published and flagged — a supported claim without the required basis gives an issue of kind `invalid_claim` (or `unresolved_reference`); `project` then sets `process_disposition: "withheld"`, `termination_cause: "unknown"`, `disposition_integrity: "invalid"` and lists the issues. The raw subprocess record is not altered. See row 2 for the full path.

## K-165-3 · C:165 · evidence

**Pass.** gates-lifecycle-profile
**Claim.** "An exit request is not proof of reap."
**Mechanism.**
1. Host driver: `ChildProcessState.terminate` records `terminationRequest` (signal, `kill` return, errno) and then waits. `status` and `ownedReap` are assigned only inside `wait` when `waitpid` returns the child's PID.
2. Producer resolver: `resolveDisposition` tests `out.reaped != true` first and returns `final_status` unresolved with reason `no_successful_reap`, whatever the request result. `kill_request_and_result` is a separate claim that is `supported("requested")`.
3. Reader: `validate_lifecycle` raises "final_status contradicts reaped status" when a supported signal or exit-code status sits beside `reaped != true`, and "terminal collection without confirmed reap" when `collection_basis` is `after_confirmed_reap` without a reap.
The cooperative exit request (`exit_requested`, stored by `ActorSession.requestExit`) is a different field from the kill request. Neither feeds `final_status`.
**When it does not hold.** published and flagged — a reply that claims a status without a reap gets `process_disposition: "withheld"`, `disposition_integrity: "invalid"` (LIFECYCLE-PATH, row 2). An honest unreaped reply shows `unconfirmed`.

## K-165-5 · C:165 · example

**Pass.** examples-reply
**Claim.** "an unreaped worker remains unconfirmed even after a successful termination request"
**Mechanism.**
1. Host, native observation (Swift, XPC host process; single-worker driver in `CWorker.swift`): `terminate()` calls `kill(pid, SIGKILL)`, records `terminationRequest = {signal: 9, rc, errno}`, then calls `wait(options: rc == 0 ? 0 : WNOHANG, stage: "after_termination")`. `wait` sets `status` (and an `ownedReap` observation) only when `waitpid` returns the child's pid; on an error it appends a `PWRunnerWaitError{stage, rc, errno}`, marks `childUnavailable` on `ECHILD`, clears `ownershipUnbroken` and returns `.failed`. The kill result and the reap result are stored in separate fields; neither is computed from the other. In the actor form, `ActorSession` reports `reaped: process.status != nil` from the same child-process type (line 745).
2. Host, claim resolution (`resolveDisposition`, Swift): the first branch for `final_status` is `if out.reaped != true { unresolved("no_successful_reap", basis: ["reaped"]) }`. It is evaluated before exit code, signal or the termination request are looked at. The termination request feeds a different question (`kill_request_and_result`, answer `requested`). Step questions additionally require `collectionBasis == "after_confirmed_reap" && reaped == true` to be "terminal"; without it an incomplete slot's result is `unresolved("basis_not_terminal")`.
3. Host, outcome classification (same file, 367-376 and 434): an unresolved `final_status` with reason `no_successful_reap` adds the problem string "process disposition unconfirmed" to the classifier's problem list (the code that turns the list into a `normalized_outcome` was not opened).
4. The reply carries the raw observations (`runner_subprocess.reaped`, `exit_code`, `term_signal`, `termination_request`, `wait_errors`) and the claim record (`runner_subprocess.disposition.questions.final_status = {state: "unresolved", reason: "no_successful_reap"}`).
5. Controller (Rust, `porcelain_admission::project`): runs `validate_lifecycle` first; if it reports any issue the projection is `process_disposition: "withheld"`, `termination_cause: "unknown"`, `disposition_integrity: "invalid"`. Otherwise it maps `final_status`: `supported/signal` -> `signaled`; `supported/exit_code` -> `clean_exit` or `nonzero_exit`; `conflicting` -> `conflicting`; `unresolved` or `inapplicable` -> `"unconfirmed"`; `termination_cause` is `"unknown"` for everything except `clean_exit`. The controller does not rewrite the reply; `data.runner_result` is published as received and the projection goes to `data.runner_sandbox_diagnostics`.
6. Copies of the rule: (a) Swift `resolveDisposition` (producer); (b) Rust `project` plus `validate_lifecycle` (reader/projection); (c) Python `tests/lib/lifecycle_oracle.py::expected_claims` (`reaped is not True` -> `unresolved('no_successful_reap')`) and `expected_projections` (anything not supported or conflicting -> `'unconfirmed'`); (d) the table in `tests/lib/lifecycle_contract.py` (`Unresolved('no_successful_reap', 'no successful reap; a successful kill request is not a reap')`, line 162, and examples at 521-524, 591-607). All four are hand-written. `DispositionResolverTests.swift` has a "disposition contract mirror" group that runs the two Python files with `--json` and compares their rows with the Swift resolver (lines 13, 118, 516, 542-544 seen by search; group body not opened).
**Who acts, and what a consumer observes.** The host decides the claim (`final_status` unresolved) from its own `waitpid` result before the reply exists; the controller translates it. A consumer sees `data.runner_result.runner_subprocess.reaped == false`, `termination_request.rc == 0`, `disposition.questions.final_status.state == "unresolved"` with `reason == "no_successful_reap"`, and `data.runner_sandbox_diagnostics.process_disposition == "unconfirmed"` with `termination_cause == "unknown"` (or `"withheld"` / `"invalid"` if the lifecycle record fails the controller's validation).
