## K-129-1 · C:129 · example

**Pass.** examples-request
**Claim.** "a missing augment refuses before worker creation"
**Mechanism.**
CLI path (the controller decides):
1. After the contract gate and selector parse, `run` resolves the runner target (`resolve_runner_target_with_registry`), then calls `resolve_augments(&mut request_value, &app_root)` for the root policy and `resolve_actor_augments` for each actor policy in the actor form.
2. `resolve_policy_augments` removes the `augments` key from the in-memory policy object; null or an empty list is a no-op. It requires each entry to be a string, requires `sbpl_source` to be a string, validates every name (ASCII alphanumeric or underscore) before any filesystem access, then reads `<app>/Contents/Resources/Augments/<name>.sb` for each name. A failed read returns `AugmentResolution::BadRequest` with code `augment_unavailable`, path `[…, "augments", "<index>"]`, message `unknown augment <name>`.
3. `policy_dossier` / `actor_policy_dossiers` turn that into `augmentation_error`. `run` builds the dossier (including `Binaries::observe` when selection succeeded), returns `tool_error` first if runner selection failed (681-683), and otherwise returns `bad_request` for the augmentation error (686-688). Both returns precede `strip_runner_selector` (692), the held serialization (696) and the client call (699). No client, host or worker is started.
4. Ordering consequence read in source: a missing augment combined with an unselectable runner reports `tool_error` (exit 2), not the augment refusal. In the actor form the root policy's refusal takes precedence, then the first actor refusal in actor order (`augmentation_error.or(error)`, line 639).

Direct XPC path (the host decides; it cannot tell a missing augment from a present one): `PWRunnerPolicySpec.init(from:)` throws `RequestContractError.unresolvedAugments` for any non-empty `augments`; `requestDecodeFailure` maps it to `unresolved_augments` at `[…, "augments"]`; `runReservedSpecimen` replies `bad_request` from the decode catch (344-361), before `admit` and `orchestrate`.

Copies: augment name resolution exists only in the controller (Rust, hand-written). The host holds a separate hand-written rule that refuses every unresolved augment list. The built-in versus external runner choice does not change the path (resolution precedes delivery for both). INFERRED: nothing else in the controller resolves augments (`sbpl-check` was not opened).

## K-129-2 · C:129 · example

**Pass.** examples-request
**Claim.** "…and leaves the input file unchanged"
**Mechanism.** The controller reads the request file once (`std::fs::read_to_string`, run_flow.rs 594) and thereafter works on the parsed `serde_json::Value` in memory; augment resolution mutates that value, not the file. There is no code that writes to the request path. I checked this by searching the non-test portion of the run-path modules for `fs::write`, `File::create`, `OpenOptions`, `fs::rename`, `fs::remove*`, `fs::copy`, `set_len` and `write_all`: none in `run_flow.rs`, `augments.rs`, `runner_select.rs`, `dossier.rs`, `request_patch.rs`, `policy_check.rs`, `evidence.rs`, `utils.rs` before their first `#[cfg(test)]`; none of the first six patterns anywhere in `runner_client.rs`; one `OpenOptions` in `sbpl_imports.rs` (line 172) that opens an import read-only. The module comment in `request_patch.rs` (lines 3-5) states the same rule as prose. On the refusal path nothing after the read touches the file at all. Direct XPC: `pw-runner-client` reads the file with `Data(contentsOf:)` (main.swift 115) and has no write to it in the lines read. The property is the absence of a writer; no component enforces it at run time.
