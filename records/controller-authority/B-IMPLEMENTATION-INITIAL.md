## Method and evidence scope

I followed CLI dispatch into actual call sites, then followed the held values, callbacks, native publications, readers and cleanup transitions. Component READMEs were navigation, not proof of their descriptions. The evidence grades used here are **S** (source-read realization), **C** (read assertions on constructed inputs or controlled dependencies), **N-route** (read a native test's route and observations, without crediting its execution). No new test, build, native invocation, registry action, worktree, commit or helper agent was used. There is **no newly inspected native execution credit** in this report. The historical CLI prerequisite is accepted by the maintainer under BASELINE's entry decision; its pruned raw runs are not available observations.

The controlling distinction is between deciding to request work and possessing an observation of work. Rust decides preparation, selection, one client launch and public assembly. The Swift client decides reservation acquisition and one execution-selector invocation. The host decides grammar/meaning admission, owns child orchestration and builds the reply. The worker calls compilation/application and attempt APIs; the validator calls the prediction API. Rust subsequently reads carried evidence; an independent consumer subsequently checks the envelope Rust constructed. These are separate authorities even where they share structural definitions.

Paths in tables are repository-relative. Symbols disambiguate their exact implementation; all source claims below have S scope unless explicitly assigned C or N-route. No static call trace establishes that a particular native path executed on this machine.

## Independent consumer and oracle audit

**B-CONSUMER-RESULT.** `tests/lib/consumer.py::validate` first gates versions, checks shapes and envelope/client consistency, calls `_validate_result`, then checks projected reply semantics. `_validate_result` obtains its outcome through `admitted_reply → runner_client_capture.admitted_host_reply`: exact complete retained host bytes, admitted capture, current producer and compiled-profile context decide applicability. It does not use `result.ok`, reported exit, normalized outcome or presence of controller assessment to decide whether to run. Unrelated reply-record errors therefore do not suppress result faults. It independently requires string outcome equality, actual Boolean success exactly for finished, and actual integer 0/1 exit; Python Boolean/integer equality is deliberately insufficient. It does not repair input.

The consumer and Rust do not have identical admission domains: the consumer explicitly does not duplicate Rust's collection-capacity geometry gate. A capacity-only refused typed reply can be interpreted by this reader and yield result inconsistency. That is an exposed coverage boundary, not evidence that Rust accepted it or that a native producer emits it. Changing this domain is a separate question from eliminating controller-authored applicability switches.

The consumer checks the reported exit relationship; it does not observe process exit. `check_example_round_trip.py` separately compares captured process exit and reported exit. A consistent non-finished reply can pass consistency and fail the case's native-success expectations.

**B-CONSUMER-CALLERS.** Text/call-site discovery found current `envelope_skeleton` use in six caller files: `blackbox_e2e/checker_controls.py` (helper xpc_error fixture with explicit false), `blackbox_e2e/runner_client_capture_controls.py` (bad_request/false), `blackbox_e2e/extension_controls.py` (ordinary finished baseline), `runner_filter_sysctl_name/checker_controls.py` (current reply), `source_drift/porcelain_codec.py` (bad_request/false, testing JSON-fixture opt-in), and `witness_contract/example_round_trip_controls.py` (absent and host bad_request refusal variants). The helper's default now follows reply outcome; explicit `ok` or later result mutation still permits intentional inconsistency. `recapture_host_reply` is fixture construction after deliberate host mutation, not consumer normalization and not suitable for transport-fault controls.

`git show 6c9f11da` verifies the default-helper change and introduction of the result rule; it does not contain a bulk rewrite of those existing caller fixtures. `c188ffb4` removes the controller-assessment applicability dependency and adds coherent/mismatched missing-assessment controls. The checked-in constructed baseline's last changes predate this rule. Thus this inspection does not claim invented fixture corrections. Current intentional result faults remain in `result_consistency_controls`; existing explicit false callers remain coherent. Broader shared-reader reach includes direct callers in blackbox, witness_contract, runner validator/outcome/filter/exec/DAC/BYOXPC/smoke suites, plus `witness_capture`, `envelope_compare`, `unavailable_prediction`, `path_diagnostics_contract`, `footprint_workloads`, source-drift codec and runner-unit reader corpus. A count of import sites is not proof every path executes; wrappers add transitive callers. A change to this consumer requires the complete default battery and affected controls, not only example cases.

| Worker evidence mapping, policy/readiness pipes, child state | Host-owned session acquires before spawn; worker inherits installed endpoints and independently maps; host FD closes after spawn, mapping lasts through output collection/teardown. Child references have their own lifetime. |
| Authority region, token buffers and native handles | Actor setup/custody/worker own them. Raw authority bytes are not Rust's evidence payload; erasure, unmapping, native release and process exit are different events. |
| Validator process/pipes/partial frames | Host launches per eligible phase, reads/associates under budgets, closes collection before release; partial frames and child status are retained independently. |
| Registry lock/pending install/cleanup record/plist/service | Lock is process-scoped; durable records and launchd resources can outlive command, interruption and test output. A completed stdout report is not required for these effects to exist. |
| Clocks, credentials and external services | Wall clock supplies timestamps; continuous/monotonic clocks govern different stage allowances. Filesystem permissions, process credentials, code signing/keychain, GUI session, launchd/XPC and OS sandbox APIs remain ambient dependencies.
