PolicyWitness architecture
This tour follows one run through the internals and across their boundaries. Read it after the README's The Experiment section and before the directory
READMEs. Each section links to the relevant field reference, contract, module list, test map or build guide.

for that id, the source symbol that implements it and the test or rule the manifest names. The generator verifies symbol presence and test definition. Follow a node

Why these processes exist
Two facts about the macOS sandbox shape everything. sandbox_check answers for a live process, and sandbox_apply is one-way: a process that has applied a
profile keeps it for the rest of its lifetime. A specimen therefore needs a fresh process that applies the policy and stays alive long enough to be queried and to
attempt things. PolicyWitness spawns one fresh worker per sandboxed process the specimen names: one for the single-worker form, one per actor for the actor
form. Each applies its own policy once (an unapplied actor applies none) and is queried from outside.
The reply path must stay outside the policy under test. A (deny default) profile can deny the worker's own writes and even its exit. The worker therefore
publishes into a shared region the host mapped and pre-touched before the spawn. The unsandboxed host assembles the reply. Published attempt, native-call and
progress records describe the worker's observations; the host separately observes process exit and cleanup. The disposition record keeps those sources distinct.
The host is an XPC service that launchd starts for one specimen and that exits shortly after replying, giving each run fresh host state. The controller is a separate
process so that an envelope is printed whatever the host does, including never answering. The controller is Rust and NSXPCConnection is an Objective-C API, so a
small Swift client owns the connection (why the launcher shells out).
The client acquires a connection-bound reservation before submitting specimen bytes. It may retry acquisition within one absolute deadline; a lost acquisition reply
cannot have executed the specimen. Immediately before execution it records submission as invoked. No later reply loss, timeout or refusal permits replay. An
unused reservation retires on expiry or connection loss; a consumed one belongs to its execution owner through reply and retirement. The user guide describes the
capture fields and the distinction between invocation, host reply and effect evidence.
Known gap: the terminal reply flush delay is best effort. A completed specimen can lose its reply if the host or connection disappears; no result retrieval or safe
execution replay is available.
The validator is its own process so that sandbox_check runs unsandboxed against the worker's PID while requested actions are held after setup. sbpl-check
supplies an independent compile diagnostic in the controller's context when an admitted client capture ends in xpc_error. The held whole request retains its
fallback diagnostic. For actors the controller additionally selects each object-valued actor policy and associates the helper result with that actor; this is not evidence
of application. Fallback can precede host admission, so the admitted actor-count bound does not bound the number of helper invocations. Per-helper retention also
does not bound their cumulative envelope or process memory; LIMITS owns those bounds.
The issuer serves the declaration form: native issuance occurs before worker creation under ordinary authority, outside the specimen policy. It receives no worker
entitlement plist. The host prepares the target and observes issuance and cleanup without calling sandbox APIs. A bounded transient channel carries the token to
the worker; only references and publication facts enter retained evidence. The worker consumes and releases in its existing phase sequence.
The actor form needs no issuer: an actor issues inside its own process, after its own setup, and the host moves the token between actors through fixed custody
buffers and per-actor authority regions it maps before launch. The host still calls no sandbox API; it copies bytes, compares them and erases them. One actor runs
requested actions at a time; parked workers still service deliveries. The handoff sequence explains completion and failure gates. No actor is designated the
specimen's singular worker in the reply.
Only the worker (compile/apply, consume/release and, in an actor, file issuance), the issuer (file issuance for the declaration form), the validator (sandbox_check)
and sbpl-check (compile only) call native sandbox APIs; the topology table's Native sandbox API column records these roles. Source and artifact checks enforce
the host's separation through source drift and artifact inspection.

Notes:
host: All authorized connections share one locked reservation slot. Only the connection holding its grant can consume it, before specimen decoding. Stale expiry or
disconnect cannot retire an executing owner; client loss after submission never permits replay.
T5: Policy delivery uses nonblocking writes under one absolute monotonic deadline (the worker_policy_transfer limit) beginning after spawn. Expiry closes input
and enters cleanup before readiness or sentinel polling. The pipe carries no framing: the host writes the submission's byte count into the shared header before
spawn, and the worker at EOF publishes the count it read and refuses a different length before compiling.
T13: Declaration form only: issuer wait 5,000 milliseconds; cleanup may overrun. Missing capability refuses declaration-form extension specimens.
T14: Token storage 16,384 bytes; raw bytes never enter reply fields.
T15: One region per actor, mapped by the host before launch and by that actor before application; a validator or another actor never maps it. Setup allowance
10,000 milliseconds; lifetime cutoff 180,000 milliseconds.
T16: Exchange allowance 5,000 milliseconds on each side; expiry is a transport status, never a native result. A later operation cannot reuse the expired operation's
payload or answer cell. Host answer and completed source action are separate observations; a source timeout can still complete its phase.
T17: Recipient framing acknowledgement precedes host byte equality and usable/failed settlement, then the source answer. Consumption requires committed,
accepted, usable settlement. Private custody erases at last declared transfer use, including failed delivery; shared teardown erasure requires a reaped or never-
launched owner.

One run in time
The host closes query collection before releasing the actions of each phase. comparison.order: "query_first" requires that phase's eligible native record and
observed collection, release, acknowledgement and ownership chain (the record). A simple probe_plan becomes one phase named main. Ordinary and
declaration requests use CWorker.swift: one worker, one policy application and all its phases. Public actor requests instead reach runActors. ActorScheduler.swift
walks their serial schedule, activating the scheduled actor's worker for each visit while others remain parked. Each actor keeps its own fresh process across its
visits. Each actor applies its policy once or declares unapplied setup. Both drivers use ActorSession.swift for launch, policy transfer, readiness, polling and cleanup.
With a declaration, admission also checks references, lifecycle caps and exec exclusion. The host then resolves the submitted target and records metadata,
launches its bundle-local issuer, and waits for its native result and cleanup. Only complete bounded issuance and confirmed clean reaping permit delivery.
Preparation failure and other issuance failures remain observations; missing helper/native issuance capability produces a named refusal before the worker. The
submitted query and attempt targets retain their original values.

Collection can close with unavailable predictions or incomplete validator cleanup. Release still requires a live, correctly waiting worker. A failed phase wait, invalid
release ordinal or loss of worker ownership prevents later actions while preserving earlier publications. A boundary publication records progress; each action
publishes its result separately. Native pre-call markers and completed result publication are distinct. A call without a published result remains unresolved even if an
independent test knows it returned. A consume/release action before an ordinary action in the same phase can change what that action encounters after its query
was collected. Read phase progress as the observed sequence of collections and actions. The worker exits after terminal publication without waiting for host
permission. The host's mapping retains its publications. An acknowledgement acquired after confirmed reap can establish the earlier phase interval while
ownership remained unbroken, including when fatal termination followed acknowledgement without done. The run retains its independently observed abnormal
disposition.

Actor handoff and schedule advancement
After setup, each scheduled visit follows activation → arrival → eligible query collection → numbered release → worker acknowledgement → ordered actions →
phase completion. Empty visits still have these boundaries. While parked, recipients service transport apparatus without running requested native actions. An issue
and transfer within the active source's actions proceed as follows:
The source issues a token, copies bounded bytes to its one-shot outbound slot, erases/frees the native allocation and commits the slot. The host validates and
copies to private custody, erases the outbound bytes, then answers accepted or rejected custody. Published bytes cannot be reused by the source even if its wait
expires.
A transfer publishes its own request cell. The host copies custody into the assigned recipient slot. The recipient validates its preassigned framing and
acknowledges while parked; a self-transfer services inbound delivery inside the source's exchange wait. Neither operation consumes the token.
The host compares accepted recipient bytes with custody, settles equal bytes as usable, then answers the source. Rejected or incomplete exchanges settle as
failed. Only committed, accepted, usable settlement permits later consume.
The source publishes the answer it observed, or its own timeout/fault, in its completed action. Host source acknowledgement requires a completed action matching
the host answer; a late answer cannot rewrite a source timeout.
The worker completes the phase after its actions return. The host services custody before checking completion and can then advance the schedule. Completion
does not require every transfer to succeed: a timed-out exchange can complete with failure. Deferring recipient acknowledgement until its activation would
therefore delay the earlier source's synchronous exchange.
A failed visit requires stopping and reaping its actor before further activation; unresolved termination cancels remaining activation, and timeout or ownership failures
can cancel even after reap. Shared authority erasure requires a reaped or never-launched owner; private host custody is erased separately. The worker resource
account gives the lifetimes. This sequence follows walkSchedule, serviceOutbound, serviceTransfer and recordSourceAcknowledgements, and the worker's 
wait_exchange and service_inbound_once. Actor authority controls and handoff mutation controls cover copying, parked acknowledgement, settlement and
quiescence dependencies.
Implementation and checking routes
Where each stage is pinned:
Controller admission and selection. run in run_flow.rs: the manifest is loaded once, then parse_request, validate_request_version, selector parsing, 
resolve_runner_target_with_registry, resolve_augments, the dossier, and strip_runner_selector before the held bytes are serialized. Checked by the 
orchestration tests in the same file.
Extension preparation and issuer lifetime. ExtensionSession records target resolution and metadata before a fresh native issuer, admits bounded publication
only after confirmed clean reap, and clears the mapping. run_targets checks placement, symlinks, preparation failure and replacement independently; run_case
drives native interruption, malformed transport and token confinement. runExtensionEvidenceTests inspects actual mapping erasure and withholds delivery after
an unconfirmed reap.
Caller authorization. authorizedCaller runs when the connection is accepted, before any request is read.
Host admission. runSpecimen decodes with closed keys, then admissionFailure(for:) (capacity), requestMeaningFailure (meaning) and 
computePolicyHash, in that order; a refusal replies without spawning anything. Checked by runner_outcome_bad_request and failure_boundaries.
Query planning. planValidatorQueries runs anew at each observed phase arrival, after all prior phase actions have completed. It drops excluded operation/filter
pairs and paths that do not resolve on the host then. path_unresolved_at_planning supplies an explicit unavailable prediction without suppressing the paired
attempt. Checked by PhaseProtocolTests, query admission tests and the planner rule in source_drift.
Spawn and apply. The driver's header comment in CWorker.swift from the region setup through the ready byte, and the worker's from mapping the region through
apply. The ready byte has its own window (readyByteTimeoutMs); runner_ready_byte_resilience checks it.
Compiled-object receipt. When the request opts in, the worker copies the compiled object into its capture region before applying it (pw_capture_profile). The
host admits that copy only after successful application, worker completion, PID, nonce, input identity and payload integrity checks (decodeProfileCapture); the 
guide defines the receipt's provenance and reading rules. In actor form the receipt belongs to the opted-in apply actor and is admitted using that actor's identity and
completion; unapplied setup supplies no receipt. Checked by CompiledProfileCaptureTests.
The barrier. The phaseBoundary callback collects against the worker's PID. The driver observes arrival and checks child ownership before collection and again
before release. Its ordinal store cannot reuse an earlier release; immutable phase acknowledgement records preserve earlier observations. PWRunnerOrdering is
assembled independently per phase. PhaseProtocolTests, OrderingTests and the opt-in order-barrier mutation control check the protocol.
Attempts and publication. run_attempt writes each slot and releases completed; an exec attempt acquires its pipes and spawn handles after apply and
releases them before its slot completes. Checked by runner_c_worker_harness and runner_exec_lifecycle.
Exit, grace and kill. The worker harness's terminal_exit_without_request and terminal_erasure controls cover autonomous exit and erasure before
publication; runner_outcome_runner_timeout/host_kills_hung_worker checks the kill path. runCWorkerLifecycleTests covers acknowledgement recovery
after confirmed reap without restoring a broken ownership chain.
Reply and envelope. reply_version admits the reply or retains it unread; fallback_policy_check runs only for an admitted xpc_error; complete_execution
projects the disposition; execution_envelope assembles the execution records. Checked by the Rust unit tests named in the boundary tables below.

The client's timeout ends the controller's wait and yields a synthetic xpc_timeout reply. Host work continues independently. The host's cleanup can fail: terminate
makes one blocking wait after a successful kill request, and when no reap is confirmed the collection basis reads execution_may_continue rather than 
after_confirmed_reap. The failure evidence contract records reply delivery, the end of observation and the end of execution separately. There is no global
lifecycle deadline.
The worker tour owns the exec-descendant limitation and explains the resources and observations retained during exec cleanup.
Each budget covers a specific stage. In the declaration form the issuer's monotonic wait, extension_issuer_wait, begins after issuer spawn and precedes worker
creation. Target preparation and spawn are outside that wait; issuer cleanup can overrun it. The client reply window includes this work, while worker and phase
collection budgets have not started. Policy delivery has its own absolute monotonic deadline, worker_policy_transfer, started immediately after the spawn; the
ready window, worker_ready_wait, covers only the wait for the ready byte after the policy has been written. In the single-worker driver the sentinel deadline, 
worker_sentinel_wait, covers application through done, less every phase collection interval, because callbacks run synchronously between polls; the validator I/
O deadline, validator_io_wait, covers one collection, capped by the remaining cumulative phase_collection_wait allowance for planning and collection
across all phases. Cleanup time is charged to that allowance but can overrun it; exhausted later phases retain unavailable predictions. The proceed budget, 
worker_proceed_wait, covers each worker phase's wait for its exact release ordinal; the grace timer, worker_exit_grace, covers exit request to kill; the exec
deadline and attempt budget, exec_child_wait and exec_attempt_budget, cover the worker's waits on exec children, per step and per worker plan, excluding
acknowledged phase release waits and, for actors, accepted parked activation waits. The worker's release wait and exec allowances count continuous Mach time,
which includes system sleep, in one validated tick domain; host waits keep their own clock, and no worker time is compared with them. The ready and sentinel
budgets are elapsed monotonic allowances: each sleep is bounded by what remains, polling costs consume it, the sentinel allowance excludes measured phase
collection intervals, and expiry starts cleanup rather than promising a total response time. These HostWaitClock waits fall back to remaining nominal sleeps on a
clock fault. Their values and checks are in LIMITS.md.
Actors instead have one setup allowance starting before authority-region preparation, one execution pool for the whole schedule excluding synchronous collection,
and one aggregate collection pool reducible by validator_total_timeout_ms. Policy delivery and readiness are capped by remaining setup time. The legacy
sentinel override does not change the actor execution pool. The shared continuous lifetime cutoff is sampled at checked worker waits; it does not preempt blocked
native calls or bound final cleanup. These allowances are distinct from the client's reply deadline and each worker's exec budget; see execution budgets.
The host sends policy bytes through a nonblocking pipe under the delivery deadline (writePolicy and MonotonicDeadline in MonotonicDeadline.swift). Partial
writes, interruptions and backpressure consume the same allowance. Expiry records policy_transfer_timeout separately from any write errno, closes input and
enters cleanup without starting readiness or sentinel polling. Counts describe writes accepted by the pipe. The worker's account of what it read is separate: the host
writes the submission's byte count into the shared header before spawn, and the worker, at EOF, publishes the count it read (policy_read in the reply) and refuses
a different length before compiling, so a delivery cut after a complete form is never applied as a shorter policy. PolicyTransferTests checks a stalled reader,
exact draining delivery, deadline edge cases, cleanup failures and the truncated delivery the shipped worker refuses after the host's timeout; the actual driver
replies pass through controller assembly and the independent consumer. The worker harness pins the refusal, the receipt and both directions of the comparison
without the host. The deadline does not bound final reap or cancel an earlier client timeout.

The validator receiver checks an exact kind and schema marker, bounded frames and strings, and per-query byte and record allowances before association. A

How the system verifies itself
The suites are listed in tests/README.md; this section names the mechanisms they are built from.
Goldens. response_shape.json and envelope_shape.json under tests/fixtures/contract/ record every key a reply or envelope can carry and its type,
collected from field-complete fixtures; they are also the readers' allowlists. abi_layout.txt is the compiled harvest of the worker ABI's sizes and offsets. A
difference writes a candidate; replacing the golden with the reviewed candidate is the acknowledgement (shape goldens).
Generators with marked regions. The 8 manifest nodes of the document graph, from the wire numbers to the prose baseline, are hand-owned facts, and the
identity is digested from the sources themselves. The 6 generator nodes, one of them the shared module, copy manifest facts into marked regions of documents
and sources, render counts and limit values into inline spans, and resolve limit placeholders in the architecture facts; the build runs every generator's check before
signing. Every check citation carries a form, and the generator verifies the definition behind a test. Prose that still states a value, a count or a citation outside these
mechanisms is listed in the prose baseline, which grows only by an explicit entry and which a release cannot grow. These documentation input manifests feed
build-time checks. The embedded evidence manifest is read by the controller during a run, as the run inventory describes.
Source-drift rules. Mechanical checks over text that is not generated, from the host invariance rule to the harness note's copies. Each rule is a citation of the drift
node in the document graph, and a test holds that list equal to the rules the script runs.
The consumer. consumer.py gates an envelope on exact versions, validates every step against its raw channel fields through the goldens, and selects steps by
field; it is the reader the suites share and the reader an external consumer is expected to copy.
Request-exposed test controls. _test_overrides can select deadlines, hangs, a self-signal, and replacement worker, validator or issuer executables. Supplied
controls are echoed when available, subject to refusal sanitization; an echo does not prove that execution reached the selected boundary. The supported keys are
the table in runner/README.md, locked to the Swift type by a drift rule, and the assertion recipe is in runner/AGENTS.md. Direct driver tests also inject process
calls, and native extension fixtures instrument separately compiled helpers; these are distinct test boundaries.
The C harness. runner_c_worker_harness drives the real worker through the shared-memory ABI from a C program with no host, so the worker's publication and
failure paths are pinned independently of the Swift driver, including the actor-mode activation wait, the declared unapplied setup and the worker's own policy hash.
The actor driver tests. runActorSchedulerTests drives the internal actor scheduler against the shipped worker and validator. Process identity, each actor's
policy and the quiescence of parked actors are checked through the kernel process table, validator verdicts against the live PID and the other sessions' own
publications, not through the scheduler's labels.
The lifecycle oracle. lifecycle_oracle.py constructs envelopes from worker records and raw facts and checks that the disposition projection says only what those
facts support, with disabled unrelated fields so only supporting evidence can decide a lifecycle claim.
The dispatcher's artifact check. Before any app-dependent case runs, the dispatcher verifies the bundle layout against EXECUTABLES, the signatures, the
embedded evidence hashes and the host's undefined symbols; fixture bundles with a damaged seal or a sandbox-importing host prove the check refuses them.
The last figure is the graph those generators and rules draw over the documents: which manifest feeds which generator, which regions it writes, which copies a rule
keeps equal, and where the build runs the checks.

BYOXPC as a variation on launch and selection
A BYOXPC runner is a copy of the XPC bundle registered as a launchd Mach service, in user or system scope, by the runner subcommands (controller/
README.md). The client connects with NSXPCConnection(machServiceName:). The host binds NSXPCListener(machServiceName:) and resolves its worker,
validator and issuer relative to its own bundle, exactly as the built-in one does. The request names the runner through the selector fields the controller strips before
XPC delivery, and the registry supplies the service name and scope. The installer signs the copy's embedded worker with the supplied identity and entitlements
19
plist, the validator and issuer with the identity alone, then the enclosing bundle, verifies the seal recursively, and the registry records each binary's signature and
entitlements as read back (sign_install_tree, read_back in runner_manager.rs). The dossier records the hashes of the bundle's service, worker, validator and
issuer files as observed before invocation and compares them with the manifest baselines
(byoxpc_run_with_a_manifest_compares_the_bundle_copies_with_its_baselines in run_flow.rs); the guide defines how to interpret these pre-invocation
observations. The registry is read by an additive loader that still accepts retired kind spellings so an old install can be listed and removed; recovery of a half-
removed install is the registry ownership procedure. Absent issuer fields in older registry records remain unknown; validation and removal still work. A current
runner copy without the issuer can serve ordinary and actor-form specimens but receives a named capability refusal for declaration-form extension specimens.
Runtime dependency is separate from the complete helper inventory required for a new installation. Shared standard/BYOXPC extension and phase controls
establish the behavior with independent binary read-back and verified owned cleanup.
--env configures the host's launchd environment. The worker's environment is not recorded in the reply; actor launches explicitly supply an empty environment,
and the single-worker launch account is in WORKER. Each worker spawns exec children with an empty environment.
The apparatus itself, from the copied bundle to the processes the policy reaches, has the last figure. Two of its facts are easy to miss from the guide's install recipe:
runner verify sends a real request, so it consumes the host it reaches, and the next request meets that host's terminal claim or encounters launchd pacing
configured by the plist's ThrottleInterval of 1 second, which does not guarantee a request-delivery time; and a selector's required_entitlements is satisfied
only by keys the worker's read-back records with the value true.
