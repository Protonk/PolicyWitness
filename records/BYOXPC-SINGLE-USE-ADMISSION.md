# Single use admission for external runner hosts

Proposed resolution: give every connection to a PWRunner host the same
synchronized request-admission state, and allow only the request that claims
that state to schedule process exit. This establishes one accepted specimen
per host while permitting explicit refusal of other requests. Reliable
queuing and readiness for the next host remain separate concerns.

Status: resolved and validated 2026-10-06. Default service controls and their two narrow reversions pass; the live two-client BYOXPC control establishes the host/worker relationship independently and verifies removal.
The final default battery passed 165/165 with no skips. The proposal and
diagnosis below preserve the investigation’s original grounding.

**Proposed change**

1. Create one admission object for the lifetime of the host and share it with
   every exported `PWRunnerService`. An atomic check-and-claim, protected by
   a lock or equivalent synchronization, must cover all connections. A flag
   on each service object cannot establish process-wide ownership.
2. Claim the host when the first `runSpecimen` request enters, after connection
   authorization and before decoding or creating children. Merely opening a
   connection must not consume the host. Once claimed, the state remains
   claimed through reply and shutdown, including when the accepted request
   produces an admission refusal.
3. Return the existing `already_ran` refusal for later requests that reach
   the service. This path must create no worker or validator and must not
   schedule host exit. It needs a reply-only path separate from the owning
   request's `replyAndExit` path.
4. Preserve the owning request's reply and exit sequence. Only that request
   may schedule the process-wide exit; a competing request must neither
   accelerate shutdown nor reopen admission.

The resulting supported behavior is one accepted request per host. Concurrent
requests, and requests arriving after the owner's reply but before host exit,
can be refused. A connection racing with process exit can still fail at the
transport boundary before a refusal is delivered. The change does not promise
that every submitted request is queued or eventually runs.

This is a useful partial resolution: single-use admission can be enforced
without introducing launchd readiness coordination or automatic retries.
Automatic retry of a request whose execution is unknown would require a
separate treatment of duplicate filesystem and other specimen effects.

If implementation is deferred, overlapping requests and requests reaching a
retiring external host remain known limitations. Serializing calls until each
reply arrives is insufficient to establish host retirement. A documentation-only
disposition would acknowledge these limitations without claiming that the
single-use invariant is enforced across connections.

**Diagnosis and grounding**

In [PWRunnerService.swift](../runner/Sources/PWRunnerCore/PWRunnerService.swift),
`PWRunnerService.didRun` is an instance property. `runSpecimen` sets it before
decoding and uses it to refuse a later call to the same object.
`PWRunnerSessionDelegate.listener(_:shouldAcceptNewConnection:)`, however,
constructs a new `PWRunnerService()` for every authorized connection. Each
connection therefore receives an independent admission flag.

The same file's `replyAndExit` schedules `exit(0)` after a reply. That exit
affects the host process and every connection it serves. A request admitted
through one exported object can thus schedule exit while another exported
object is executing a different specimen. The existing `already_ran` path
also calls `replyAndExit`; simply sharing the Boolean would leave a rejection
able to schedule exit independently of the owning request.

The external launch path in
[main.swift](../runner/Services/PWRunner/main.swift) binds one
`NSXPCListener(machServiceName:)`. The launchd plist generated by
[runner_manager.rs](../controller/src/runner_manager.rs) registers that named
service. The host has no shared request claim in either path.
The [runner README](../runner/README.md#external-runner-services) promises
one specimen per runner process. The gap is between that process-level
promise and admission that is scoped to an exported connection object.

The affected trigger is two requests delivered through distinct connections
to the same still-running external host. They may overlap in execution, or
the second may arrive in the interval between the first reply and host exit.
The first scheduled exit can interrupt another request. This consequence
follows from the source paths; its live timing and observed client error
have not been measured in this investigation. Missing replies must not be
interpreted as evidence that a specimen never started or that its children
have stopped.

**Validation for the proposed change**

- Exercise distinct service objects sharing the same admission state. Exactly
  one request may acquire it, including when requests race. A connection that
  has not sent a request must not consume admission.
- Observe exit scheduling independently of response contents. A rejected
  request must schedule no exit, both while the owner is active and after its
  reply. The owner's admission failure must still consume the host and follow
  its own exit path.
- Use a live client with two authorized connections to one owned BYOXPC
  service. Hold the first request at a controlled worker boundary, then
  submit a second request. Observe worker creation and effects independently
  of response labels: only the first request may create children or perform
  its plan, and the rejection must not prevent it from finishing.
- Cover reuse during shutdown separately from normal overlap. Keep the claim
  terminal until process exit; establish that a newly launched host can then
  accept a request. Record a transport failure during teardown as such, rather
  than requiring delivery of a refusal from an exited host.
- Retain ordinary built-in and external-runner execution coverage and caller
  authorization controls. Changes under `runner/Sources/` require worker
  identity regeneration and the applicable signed-build and source-drift
  checks. The runner's [test instructions](../runner/AGENTS.md) distinguish
  unit controls from tests that require live XPC and launchd.

The stopping point is enforced single-use ownership plus an explicit
concurrency/readiness limitation. Queuing, transparent retry and a broader
host/child cancellation design are not required for that result.
