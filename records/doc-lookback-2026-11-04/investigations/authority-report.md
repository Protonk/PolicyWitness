## A1 — actor transfer timeline warrants a locally understandable account

**Confirmed documentation gap, not a demonstrated implementation defect.** Addresses ARCHITECTURE F2/F4/F9/F10: lines 75–82, 140–151 (T15–T17), 160–232, 391, B18/B19; WORKER A2 and lines 370–380, 408–437; consistency C0-4. Existing narrative already says parked recipients validate without consuming and host settlement precedes use. That is important contrary evidence against calling the document wholly wrong. The missing piece is the connection to source completion and the next activation.

Checked owners: [ActorScheduler.swift](../../../runner/Sources/PWRunnerCore/ActorScheduler.swift), `launchAndSetUp`, `walkSchedule`, `stopActor`, `finish`; [AuthorityCustody.swift](../../../runner/Sources/PWRunnerCore/AuthorityCustody.swift), `service`, `serviceOutbound`, `serviceTransfer`, `recordSourceAcknowledgements`; [pw_probe_runner.c](../../../controller/tools/pw_probe_runner/pw_probe_runner.c), `wait_for_activation`, `wait_for_proceed`, `wait_exchange`, `attempt_extension_issue`, `attempt_extension_transfer`, `attempt_extension_consume_actor`, `run_attempt`, and the `visits` loop.

The implemented sequence is:

1. Host establishes each actor's setup eligibility (applied or declared unapplied, identity and required authority setup), then walks a serial schedule. It stores one actor's activation ordinal and waits for arrival. Worker parked waits may validate inbound transport frames, but run no requested native action.
2. After arrival, host invokes collection against that actor, closes collection, checks premature publications and prior local completion, and stores release only while the actor remains eligible. Worker acknowledges the matching release before running the visit's actions in order. This is a phase ordering barrier, separate from authority transport acknowledgements.
3. Issue calls the native issuer in the active actor. A bounded token is copied to that issue's unique outbound slot; the native allocation is erased/freed before outbound commit. Commit gives payload ownership to host. Host validates, copies into private custody, checks copied framing, erases outbound token bytes and length, and only then stores its accepted/rejected custody acknowledgement. The worker's exchange can expire before that host answer; it must not erase or reuse host-owned published bytes.
4. Transfer publishes its unique persistent request cell and waits. Host services outbound publications first, then at most one pending transfer per service pass. If custody and recipient are usable, it copies into the recipient's assigned inbound slot and commits. Recipient validates framing against its pre-application source/action/delivery snapshot and acknowledges while parked; self-transfer services inbound while the source is itself in `wait_exchange`.
5. Recipient acceptance is neither consumption nor permission. Host reads the accepted bytes for equality against custody. Equal bytes produce `settled=1`, then a delivered answer to the source. Rejection, mismatch or incomplete delivery produces failed settlement (`settled=2`) without host erasing under the recipient's framing reader. Private custody retires at the token's last declared transfer use even when delivery fails.
6. Source action records the answer it actually observed, or its own timeout/clock-failure status, then publishes its completed slot. The worker publishes phase completion after all its actions return. Host records source acknowledgement only when the completed source action's transfer status matches the host answer. A late host answer cannot retroactively change a source timeout into acknowledged delivery.
7. Each host completion-loop pass services custody before inspecting phase completion. Successful phase completion permits the next schedule entry; it does **not** require every declared transfer to succeed or every source acknowledgement to be true. A timed-out exchange can still have a completed action/phase. Worker consumption independently requires the named inbound slot to be committed, accepted and settled usable. On visit failure, host stops the actor and must establish reap before allowing progress; unresolved termination cancels remaining activation. Timeout/ownership failures can cancel even after reap.

Therefore moving recipient acknowledgement to its later scheduled visit would remove servicing that the earlier sender's synchronous exchange depends upon. With the present serial schedule, that change can yield exchange expiry; it is not a harmless polling optimization. This does not prove an infinite deadlock: the waits and refusal paths are bounded/checking mechanisms, and source timeout may still allow phase completion. Do not replace this nuance with an all-deliveries-success barrier claim.

**Remedies.** Add a short actor sequence in authored ARCHITECTURE alongside an explicitly scoped ordinary timeline. Keep wire offsets, numeric waits and resource teardown in their owners. WORKER should distinguish parked transport servicing from requested actions and link to that sequence. Generated topology/boundary wording is owned by `docs/architecture.json` and `docs/generate_architecture.py`; modify inputs, not generated regions. T17 and transfer writer shorthand should name recipient acceptance versus host settlement/answer versus source publication. Keeping the current scattered account fails the architecture reader's central dependency task. Simplifying runtime gates instead would change semantics and needs separate design/evidence; current findings do not justify it.

## A3 — failed release is not a retry or revocation contract

WORKER Q2, lines 323–355 and `s37`: source resolves local state but not native permission consequences. Legacy `attempt_extension` sets `release_decided` before eligibility/native call and retains `extension_handle`; a later repeated request is unavailable even following failure. Actor `attempt_extension_release_actor` does not clear `handle_valid` or overwrite the handle after either success or failure. However [ActorPlan.swift](../../../runner/Sources/PWRunnerCore/ActorPlan.swift) refuses a second release of the same handle (`repeated_release`) and enforces ownership. Its table retention does not create a public retry capability. Both forms require a candidate handle from consume for a native release. No new implementation issue is established; retained bits and native authority state are different subjects.

A short form-scoped statement can answer Q2 if desired. No retry behavior should be added merely to resolve reader uncertainty; that would be a new API/meaning decision requiring coordinated admission, native, reply and reader work. Successful or failed release still needs a separate fresh-access observation for the experiment's access question. Source inspection supports these local transitions; this report claims no native retry experiment.

## A4 — digest question bounded and dismissed from this change

WORKER Q1: consulted native-extension evidence contract and the authority implementation describe local reference association, withheld token bytes and separate bearer storage. Search of `docs/CONTRACT.md`, `docs/EXTENSIONS.md` and `tests/FAILURE-PROPAGATION-CONTRACT.md` found no explicit token-digest retention contract. A hypothetical digest does not establish permission, native identity or cause. There is no demonstrated documentation defect or standalone implementation task here; retain the existing distinction and stop this branch.
