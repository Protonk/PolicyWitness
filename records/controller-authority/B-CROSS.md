## X02/X04 — association operands and the meaning of retained actor endings

**BC02: distinguish producer request fidelity, recipient carried consistency, and subprocess-local consistency.** The apparent original-request mismatch is not established by the inspected contract. `actor_evidence.actor.account`, `actor_evidence.gate.prepared_association`, and `equipment.preparation_failure.retain` assign request-to-reply assembly obligations to the host. The preparation children `counts`, `actor_identity`, and `phase_identity` name the request/reply operands. `actor_evidence.actor.reader_scope` instead assigns recipients checks of ordinary carried relationships. These are different obligations with different available inputs. `porcelain_admission::execution_diagnostics` and its semantic `admit_reply` receive a typed reply, not the prepared request; `porcelain_actor::validate` likewise operates on the reply. The Python consumer cannot prove that an internally consistent replacement actor/action account is the one originally submitted merely by joining its own fields.

The profile receipt follows the same separation. The host PID and nonce capture rules in `35-profile.surface.md` require the captured PID to match the owned worker and the nonce to match the request. The controller's `labels` check explicitly says the nonce, payload, digests, lengths, and counts remain host assertions; it checks captured/unavailable context labels after producer/capacity admission. Absence of a controller request-nonce comparison therefore is not, by itself, a violation of that rule.

Suggested clarification near `actor_evidence.actor.reader_scope`: “Recipient checks compare the actor, phase, action, launch, and subprocess records carried in this reply. They do not independently compare these declarations with the submitted request. The host owns request-to-reply assembly.” If request-bound consumer certification is desired, that is a new product requirement requiring explicit operands, interface changes, and refusal semantics; do not describe it as an already implemented check.

**BC04: local actor projections have dependencies on joins that can subsequently fail.** The current contract accurately promises retention, but calling every retained ending “independent” overstates its association strength. In `porcelain_admission.rs::execution_diagnostics` the projection:

1. selects phases by equality with the carried actor label;
2. flattens their carried action IDs;
3. finds the first global step or extension event with each ID;
4. projects the actor's carried subprocess against that action list;
5. copies the actor label onto the result;
6. later runs reply-wide checks, which can invalidate the aggregate without changing those actor results.

`validate_lifecycle` checks the subprocess record and selected actions, including PID range, local exit/reap declarations, disposition steps, and local native references. It does not take the actor's launch record or owned-reap record. `actor_associations` separately checks label/index uniqueness, launch/subprocess PID agreement, visits/phase relationships, and action/event associations. `porcelain_actor::owned_reap_valid` separately joins launch PID, subprocess PID, owned-reap PID/native return/status, and reap/capture declarations. Those checks can reject the very association needed to attribute a plausible local subprocess ending to a declared actor.

Consequently, these source-derived cases matter: a valid-looking local subprocess beside a conflicting launch PID; duplicate actor labels that select the same carried phases; or duplicate action IDs where first-match selection supplies an action before a global uniqueness finding. These are proposed focused controls, not newly executed counterexamples. A local `clean_exit` can still describe the selected subprocess record while attribution to the intended actor/action sequence is uncertified. There is no evidence here that the native host emits these inconsistent ordinary records; this is about recipient behavior on carried inconsistency.

`diagnostics.execution.reply_checks`, `diagnostics.issue.subject`, and the open `withholding_scope` gap explicitly retain actor assessments after reply-wide invalidation. Current implementation therefore matches the present retention policy. Recommended descriptive wording: “Each actor assessment describes the carried subprocess and the action records selected through carried labels and IDs. A reply-wide association finding can invalidate attribution of that assessment to an actor or action sequence even when its local disposition integrity remains valid.” Put this beside the preservation rule, not only in a remote limitations section.

If stronger withholding is selected, distinguish an unrelated global error from a failed dependency of this actor's assessment. Blanket removal of all actor endings is not entailed by these findings. `typed_invalid_actor_account_keeps_independent_actor_endings` confirms retention with an invalid actor account; it does not isolate every launch-PID, duplicate-label, or action-selection dependency. A future dependency-sensitive policy needs those controls and explicit public scope. Evidence that a particular dependency is checked inside `project`, or a contract assigning original-request comparison to this recipient, would change my assessment; neither was found in the inspected paths.

## X05 — degraded associations

**BC05: reporting degradation deliberately reduces validation scope.** The `reporting_failure` branch checks the degraded summary/marker and the prohibition on comparisons, while bypassing ordinary actor/phase association validation. Subprocess-local lifecycle projection still runs; its comparison limitation differs in degraded mode. The host's `pwRunnerReportData` first attempts a rich degraded report retaining assembled records, then can fall back to a minimal scalar report if validation/encoding still fails. Retention does not repair the association that provoked degradation.

The `reply.failure.publish.associations` gap already describes this choice. This is not an ordinary-association promise contradicted by code. Suggested wording at the retained-record rule: “Degraded records remain available for inspection. Acceptance of the reporting-failure form does not certify ordinary actor, phase, action, launch, or custody associations; local assessments do not restore that certification.” A requirement to validate a bounded subset of those joins is a product change. The scope and fallback behavior must be decided before selecting such checks. A rich-report fixture passing form checks is not evidence that all its associations were checked.

## X03 — exact result mapping

**BC03: the current success rule is implemented as written.** After reply admission, `run_flow::complete_execution` computes execution diagnostics, independently obtains the host normalized outcome, then sets `ok = outcome == "finished"` and exit code `0` for that case, `1` otherwise. Failed native attempts, semantic findings, or a withheld/invalid disposition do not switch that mapping. Earlier delivery, decode, producer, geometry, and profile-context refusals follow their own paths; they are not admitted `finished` replies. Unknown admitted outcomes are unsuccessful, not alternate success spellings.

`diagnostics.execution.outer_result` and the result-selection rules agree. The open `envelope.data.select.success_findings` node is a maintainer decision, not evidence of an implementation defect. Suggested current wording: “For an admitted reply, `result.ok` and exit code report whether the host summary is `finished`. They do not certify an empty controller finding set or successful native actions. Inspect the retained attempts and execution diagnostics separately.” Changing the rule would affect Rust, consumers, fixtures, and public expectations together.

Fresh result controls provide scoped corroboration: `finished_record_error_and_exit` records both the wrong-exit finding and `fs_write_allowed: missing comparison`; `assessment_absent_mismatched` still expects the three outer-result disagreements without using assessment presence as admission; `projection_differs_from_bytes` records the exact-host-bytes mismatch plus the three result disagreements. These are constructed reader controls, not native faulty-host executions. Their incomplete full-error oracle is discussed below.

## X06 — publication is command-specific

**BC06: do not transfer the example emitter's guarantee to all commands.** `example.rs` renders, uses `write_all`, explicitly flushes, and maps failure to exit 2 with discard semantics. `cmd_run` and `json_contract::print_envelope` use `println!`; ordinary publication is not an equivalent fallible write/flush protocol. Rendering success and a computed result code do not establish successful receipt by a downstream reader. A pipe failure can occur after native effects; it does not undo execution or promise cancellation.

I found no general contract requirement that every stdout failure produce the example command's exit-2 behavior. The version success/rendering rule is not an explicit durable-delivery promise. Thus the immediate correction is precision of scope, not a demonstrated cross-command compliance fix. Suggested common wording: “Result selection describes the envelope if published. This rule does not establish downstream receipt or rollback after publication failure. The example command separately specifies its write/flush failure behavior.” If maintainers want one publication policy, choose it explicitly, including partial output, flush, error channel, and post-effect failure; then apply it at the real emission sites. Successful captured output only exercises the success path.

## X07 — a complete independent expected-error oracle

**BC07: minimally fix the test comparator, not the consumer.** `tests/suites/blackbox_e2e/checker_controls.py::result_consistency_controls.control` currently extracts recognized result prefixes into a set-like list, checks required companion substrings, and rejects all extras only for cases expecting no errors. It permits unexpected non-result diagnostics and does not count duplicate recognized errors. Fresh success therefore proves the narrower predicate, not an exact full diagnostic set.

Keep the existing fixtures, production reader, admission policy, and result mapping. Author an expected complete diagnostic multiset for every case in this function, including schema/type findings and structural companions. Compare `Counter(actual_errors)` with `Counter(expected_errors)` without dropping unknown messages. Expected values should come from each independently authored mutation and its public expectation; small formatting helpers may interpolate explicit case constants, but must not call `validate`, infer expected errors from actual output, or reimplement admission/result interpretation. Keep any result-category summary as reporting only. Treat the special unsupported-version case with the same completeness rule.

For example, `finished_exit_boolean` currently records both `envelope.result.exit_code is boolean, not number` and `result.exit_code is false, not 0 for the admitted reply outcome "finished"`. An exact expectation must demand both. The record-error-and-exit case must demand its result diagnostic and exact missing-comparison diagnostic. Review expectations independently against the fixture edits and consumer/schema obligations; copying a passing receipt wholesale would preserve a circular oracle.

Add a small sensitivity control around this test-only comparator using an independently specified complete expected list. The exact list must pass; adding one unrelated diagnostic must fail; removing one required diagnostic must fail; duplicating one diagnostic must fail. Catch the expected comparator assertion in the control and fail if it accepts. This directly demonstrates the weakness has been closed without mutating the consumer, interpreting another contract, or executing another native run. Report expected/actual full lists and the sensitivity outcomes in the existing artifact. This is a narrow test correction, not a fourth interpreter. I have not implemented or run it under this read-only assignment.

## X08 — reader capacity domain

**BC08: the Python admission domain intentionally differs at capacity.** Rust `reply_geometry` gates bounded collection sizes before projection/joins; ordinary CLI admission can refuse on this basis. `tests/lib/consumer.py::admitted_reply` requires supported envelope/reply identities, exact captured host bytes, producer context, and receipt labels, but explicitly does not restate the controller's collection-capacity gate. Its comment warns that capacity-only refused replies are outside its intended reading domain. It can consequently compare the envelope against a reply Rust refused and emit a result inconsistency. That is not evidence that Rust ignored its result rule.

Do not claim universal agreement between independent readers. Suggested statement at consumer applicability: “This consumer's admitted-result comparison assumes the reply is within controller capacity bounds; it does not independently establish that condition.” Prefer an explicit unsupported/not-evaluated scope if the consumer is later exposed to arbitrary capacity-refused artifacts, but that would require a chosen applicability representation. Adding the same capacity implementation merely to force agreement can weaken independence and is not necessary for the X07 comparator repair. Evidence of a currently promised capacity-inclusive consumer domain would turn this into a mismatch; the inspected account instead limits it.

## X10 — verify and administration

**BC10: verify PID is a host-result projection, not a universal worker-PID claim.** `runner_commands::cmd_runner_verify` admits the reply before `project_verify_typed_reply`; the admitted path projects the reply's top-level PID and maps `finished` to 0, other outcomes to 1. Delivery failure returns `tool_error`/2 with null PID; refused reply returns its refusal/1 with null PID. A top-level PID can identify the host on a host-side failure. The contract field `installation.verify.runner_pid` already says its worker/host role follows the host result lifecycle. No rename or implementation correction follows from the field name alone. Suggested help clarification: “PID from the admitted host report; inspect the report lifecycle to determine whether it denotes the worker or host.” Verify's fixed allow-all empty-plan exchange proves the scoped verification operation, not an arbitrary future specimen's behavior.

The installation rules also distinguish command success from operational absence/validity. Remove can return successful command handling while cleanup remains retained; validate can complete with invalid entries counted. Durable pending-cleanup ownership, explicit service/scope/bundle identity, and verified absence govern retirement. These outcomes match the inspected contract; changing `ok` to mean all removals complete or all installations valid is a product decision. Do not silently erase retained records on success. The fresh run discussed here supplies no new installation/cleanup native evidence.
