## K-147-1 · C:147 · example

**Pass.** examples-reply
**Claim.** "a foreign helper envelope claiming compilation cannot supply a successful policy-check status"
**Mechanism.**
1. The helper is `sbpl-check`, launched by the Rust controller as `sbpl-check --request -` with the held request string on stdin (`run_policy_check`). The controller launches it only when the client capture is accepted, request delivery did not fail, and the client's terminal event is `xpc_error` (`RunnerClientRun::fallback_eligible`, called through `fallback_policy_check` and `actor_fallback_checks`). On every other path `data.policy_check` is null.
2. `parse_policy_check_output` takes the helper's process output. It calls `capture_json_output` (in `controller/src/utils.rs`, not opened) to get a text capture and an optional parsed JSON value.
3. It picks `status` in this order: `capture_error` if stdout capture failed; `parse_error` if stdout did not parse; `tool_error` if nothing parsed; otherwise the result of `supported_outcome(env)`, or `invalid_reply` when that returns `None`.
4. `supported_outcome` returns `None` unless, in this order: `kind == "sbpl_check"`; the controller's own `BUILD_CONTRACT` is not `"unbound"` and `build.contract` is a string equal to `BUILD_CONTRACT`; `result.normalized_outcome` is a nonempty string. Only then does it return that outcome string, which becomes `status` verbatim. The contract comparison precedes any read of `result`. Nothing reads `data.compile`, `data.compiled`, `result.ok` or the process exit code to form the status.
5. The parsed envelope is stored unchanged (as a `serde_json::Value`) in `policy_check.envelope` whether or not it was supported; the exit code goes to `tool_exit_code`.
6. So a helper envelope with `build.contract` different from the controller's, `result.normalized_outcome: "ok"` and any compile record yields `status: "invalid_reply"` with the envelope retained.
7. The decision is made by the controller (Rust), in one function. A second, hand-written copy of the same rule exists in the Python test reader `tests/lib/consumer.py::_validate_policy_check_reply`: it recomputes "admitted outcome" from `kind`, `build.contract == expected_contract` and a nonempty string outcome; when there is no admitted outcome it reports an error unless `status` is `invalid_reply` (or the envelope is null with a transport status); when there is one it requires `status == outcome`. Neither copy is generated. No Swift copy exists for this rule (the Swift side does not read helper envelopes; INFERRED from finding no `policy_check` reader outside the controller and `tests/lib`).
8. The run envelope's own `result` is not derived from `policy_check` on any path read (`run_flow.rs:711-745`): `policy_check` is attached to `data` after the outcome and exit code are already chosen.
**Who acts, and what a consumer observes.** The controller acts, as a reader of the helper's stdout, before the run envelope is emitted. A consumer sees `data.policy_check.status == "invalid_reply"` (not `"ok"`), `data.policy_check.envelope` holding the foreign envelope as parsed, and `data.policy_check.tool_exit_code` as received; the same applies per actor under `data.actor_policy_checks[].policy_check`.
**Sources.** `controller/src/policy_check.rs` : `supported_outcome` (lines 47-60), `run_policy_check` (65-75), `parse_policy_check_output` (77-101), `PolicyCheckCapture` (19-31); `controller/src/runner_client.rs` : `fallback_eligible` (642-652); `controller/src/run_flow.rs` : `fallback_policy_check` (371-379), `actor_fallback_checks` (from 385), call sites (715-717, 732-740); `tests/lib/consumer.py` : `_validate_policy_check_reply` (273-291), dispatch from `validate_shape` (315-317).

## K-147-6 · C:147 · evidence

**Pass.** short-regions
**Claim.** "Unsupported received bytes remain available without inferred claims."
**Mechanism.** Three paths.
1. Rejected client capture (wrong fingerprint, foreign contract, malformed, or delivery failed): the controller keeps the retained stdout bytes as `runner_client.transport: {format: "porcelain", data_base64}`, sets `transport_admission` to `unsupported`, `malformed` or `delivery_failed`, `submission: "unknown"`, and no reply (`runner_client.rs:773-783`). Retention is capped at `RUNNER_CAPTURE_BYTES`; over the cap the status is `malformed` and the prefix is kept (`:665-667, 699-701`).
2. Refused host reply inside an accepted capture: the typed capture is kept, including `runner_reply.data` with the host's bytes; `runner_reply_error` is set; the reply is `None`, so `data.runner_result` is null and no diagnostics are derived (`runner_client.rs:735-771`, `run_flow.rs:731`).
3. Helper envelope: a stdout that parses is kept as a parsed JSON value under `policy_check.envelope`, not as bytes; a stdout that fails to parse or is truncated is kept as text (`utils.rs:163-183`, `policy_check.rs:28-30, 95-100`). The status is `invalid_reply`, `parse_error` or `capture_error`.
**Who acts.** Rust controller — stated in the sentence: no
**Compared with what.** n/a; this is what the reader does after the refusals in rows 17, 25, 30 and 31 — stated in the sentence: no
**Boundary.** Controller side, after receipt, at presentation — stated in the sentence: no
**Consequence.** A consumer finds the bytes as base64 (paths 1 and 2), or a re-serialized JSON value or text (path 3), with null `runner_result` and no outcome copied from the unsupported body — stated in the sentence: partly ("remain available"; where and in what form are not stated)
**Sources.** `controller/src/runner_client.rs` : `parse_runner_client_output` (658-785); `controller/src/utils.rs` : `capture_json_output` (158-190); `controller/src/policy_check.rs` : `PolicyCheckCapture` (19-31)
**Checks.** `controller/src/runner_client.rs` : `producer_gate_precedes_malformed_descendants_and_keeps_raw_bytes` (1226-1265), `arbitrary_rejected_host_bytes_survive_and_do_not_become_claims` (1290-1305), `malformed_capture_keeps_exact_bytes_and_no_recovered_submission` (1347-1371), `unsupported_protocol_and_delivery_failure_preserve_boundaries` (1374-1389) — test — default (rust.unit) — constructed frames, observe byte-equal retention, no reply, `submission: "unknown"` for rejected captures — reaches the claim: yes for paths 1 and 2.
`controller/src/policy_check.rs` : `unsupported_or_incomplete_envelopes_are_invalid_replies_retained_unchanged` (226-234) — test — default (rust.unit) — constructed helper output, observes the retained value equal to the parsed input — reaches the claim: yes for path 3 as a value; no check compares bytes.
