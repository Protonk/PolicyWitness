## K-63-1 · C:63 · example

**Pass.** examples-request
**Claim.** "a foreign assertion plus an invalid runner selector reports the contract refusal"
**Mechanism.**
CLI path (the controller decides; the host is never contacted):
1. `run` collects host facts, parses arguments, resolves the app root, loads the evidence manifest once and builds app provenance. An argument error (for example an invalid `--runner-mode` flag value) returns `tool_error` here, before the request file is read.
2. The request file is read once with `std::fs::read_to_string` and parsed with `parse_request` (must be a JSON object).
3. `validate_request_contract` calls `validate_contract(value, BUILD_CONTRACT)`. A string `contract` equal to the compiled `BUILD_CONTRACT` (and that constant neither empty nor `"unbound"`) passes. Any other string returns `unsupported_contract`; absent returns `missing_field`; null returns `missing_value`; any other type returns `type_mismatch`. All four carry `path: ["contract"]` and `expected_contract`.
4. On error `run` returns through `refused_request` -> `bad_request`: exit code 1, `result.normalized_outcome: "bad_request"`, `data.request_failure` set, `runner_client` and `runner_result` both `None`.
5. Only after step 3 passes does `run` apply `--runner-mode` (`inject_runner_mode`) and call `parse_runner_selector_value`, which is where an invalid selector (wrong type for `runner`, unknown key inside `runner`, bad mode, bad entitlement entry) would be refused. So with both faults present the selector is never examined.

Direct XPC path (the host decides; there is no selector step to order against): the client forwards the file bytes unchanged. `PWRunnerRunSpec.init(from:)` checks `contract` first (contains / not null / string / equal to `PWBuildContext.contract` and not `"unbound"`) and throws `PWRunnerRequestFailure` with the same four codes. Only then does it call `rejectUnknownRequestKeys`, under which `runner` (not among the host's `CodingKeys`) would be `unknown_field`. `runReservedSpecimen` catches the throw and replies `bad_request` with `request_failure` from `requestDecodeFailure`.

Copies of the rule: two, both hand-written. Rust `validate_contract` (`controller/src/request_patch.rs`) and Swift `PWRunnerRunSpec.init(from:)` (`runner/Sources/PWRunnerCore/PWRunnerRequest.swift`). The compared value is compiled in on each side: Rust `BUILD_CONTRACT` from `option_env!("PW_BUILD_CONTRACT")`, Swift `PWBuildContext.contract`. The Python harness does not re-implement the gate; it supplies the candidate contract (`tests/lib/build_context.py`, not opened) and compares outputs.
