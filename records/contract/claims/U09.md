## K-159-1 · C:159 · example

**Pass.** examples-reply
**Claim.** "a foreign host reply inside a current envelope yields one unsupported diagnostic"
**Mechanism.** Three places apply a producer-contract rule to a host reply; they sit at different points and give outputs of different shape.
Path 1, the controller reading the client capture (production path):
1. `pw-runner-client` returns a binary capture containing the host's reply frame as bytes. `parse_runner_client_output` (Rust controller) admits the capture, then calls `porcelain::decode_bound::<PWRunnerRunResult>(&raw.data, false, BUILD_CONTRACT)` on the host frame.
2. `decode_bound` checks, in order: frame size, magic `PWP1`, minimum length (else `Malformed`); the 32-byte shape fingerprint against `porcelain_records::FINGERPRINT` (else `UnsupportedSchema`); then it reads only the root record's first field, the producer context, and extracts `contract`; if `expected == "unbound"` or the contract differs it returns `UnsupportedContract(contract)` without decoding any other field; only otherwise does it call the full `decode`.
3. On `UnsupportedContract` the controller sets `run.runner_reply_error = ReplyError{refusal: UnsupportedContract, message: "runner reply has foreign contract <value>"}` and returns no typed reply. The capture, including the raw reply bytes, stays in `run.transport` as `TransportCapture::Typed`.
4. `run_flow::admit_reply` calls `client.failure()`, which maps `UnsupportedContract` (and `UnsupportedSchema`) to the outcome `"unsupported_runner_response"` with that message, and returns `ReplyAdmission::Refused`. The run flow assigns exit code 1 and builds the envelope with `execution_only(...)`: `runner_result` null, `runner_sandbox_diagnostics` null. `fallback_eligible` is false because the terminal event is `runner_reply`, so `policy_check` is null.
5. The message text appears in two fields of the one envelope: `result.error` and `data.runner_client.runner_reply_error` (the latter is serialized as the message string alone, per the assertion at `runner_client.rs:1332-1336`). There is one outcome code.
Path 2, the controller given an already-typed reply (reachable only through the injectable `deps.client`; INFERRED unreachable in production because step 2 uses the same `BUILD_CONTRACT`): `admit_reply` calls `reply_version` -> `reply_contract`, which returns `ReplyVersion::Unsupported(contract)` when `reply.producer.contract != BUILD_CONTRACT`; `admit_reply` returns `Refused{outcome: "unsupported_runner_response", error: "runner reply carries contract <v>; this controller reads only <BUILD_CONTRACT>"}`; exit 1. Here `data.runner_client.runner_reply_error` is not set by this branch.
Path 3, the Python test reader (`tests/lib/document_versions.py::version_errors`, called first by `consumer.validate`): for an envelope it checks `build.contract` first and returns one error if that fails; otherwise, if `data.runner_result` is an object, it checks `runner_result.producer.contract` and returns exactly one string, `unsupported runner response: contract ... (expected ...)` for a different string or `malformed runner response: missing or nonstring contract` otherwise. `consumer.validate` returns that list without further checks (INFERRED from the single-error assertions; the body of `validate` after line 902 was not opened). This is the only reader for which the sentence's literal shape, a foreign `runner_result` inside an envelope whose own `build.contract` is current, is the input.
The Rust and Python rules are separate hand-written implementations. The Swift host has its own frame-encoding side but takes no part in this reader-side rule.
**Who acts, and what a consumer observes.** In the product, the controller acts while reading the client capture, before any envelope exists: a consumer sees exit status 1, `result.normalized_outcome == "unsupported_runner_response"`, `result.error` naming the foreign contract, `data.runner_result == null`, and the unread reply bytes under `data.runner_client.transport.runner_reply`. In the test harness, a Python reader acts on a finished envelope and returns a one-element error list.

## K-159-2 · C:159 · example

**Pass.** examples-reply
**Claim.** "... without recovered comparisons" (no comparison from the foreign reply is interpreted or reported as a comparison)
**Mechanism.** The answer differs by path.
Path 1, production controller: `decode_bound` returns `UnsupportedContract` before any field other than the producer context is decoded, so no typed reply exists. The envelope is built by `execution_only` with `runner_result: None` and `runner_sandbox_diagnostics: None`. The foreign reply's bytes are published undecoded under `data.runner_client.transport.runner_reply` (base64 in JSON, per `old_response`'s use of `data_base64`). A consumer who decodes those bytes on its own would find steps and comparisons there; the controller does not.
Path 2, controller with an injected typed reply: `admit_reply` refuses, but the run flow passes the typed `runner_result` to `execution_only` unchanged ("A decoded reply stays in the envelope on every refusal", `run_flow.rs:709-710`), so `data.runner_result` in the envelope equals the foreign reply in full, including any `steps[].comparison` it carries. `runner_sandbox_diagnostics` is null, so the controller derives nothing from it. This path is reachable only by supplying `deps.client` (tests); INFERRED unreachable from real client output because path 1 uses the same constant.
Path 3, Python test readers: `consumer.steps`, `consumer.lifecycle` and `lifecycle_adapter.read_lifecycle` raise `ValueError` carrying the version diagnostic for such a document (per the assertions at `checker_controls.py:468-474`; the gate is `document_versions.require_supported`, imported into `consumer.py` at line 30 as `_gate`; the call sites inside `steps` and `lifecycle` were not opened, INFERRED).
**Who acts, and what a consumer observes.** In the product the controller withholds by never decoding: `data.runner_result` is null and `data.runner_sandbox_diagnostics` is null, with the raw reply bytes still present in the client capture. In the harness, a reader of a finished envelope refuses by raising before it touches `steps`.
