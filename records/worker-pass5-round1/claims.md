## C2 — Exec-child stdio delivery assumes pipe descriptor numbers do not overlap the destinations

**Classification: untested lead, supported by the file-action sequence.** I have not reproduced it in a native process or established that an ordinary XPC host creates this starting state.

Challenged sentence: “The child receives explicit null-device stdin, captured stdout/stderr, an empty environment and a new process group” (`docs/WORKER.md:383–385`). The corresponding map claims are W35, “Child receives output endpoints as stdout/stderr” (`docs/architecture.json:9734`), and S34b's “Yes, duplicated as 1/2; originals explicitly closed.” The tour acknowledges arbitrary inherited worker descriptors and host low-descriptor collisions, but does not state a low-descriptor precondition for the worker-to-exec-child path.

**Source/branch:** `exec_resources_acquire` uses the descriptor numbers returned by two `pipe` calls without raising them above stdio (`pw_probe_runner.c:824–838`). It registers stdin `addopen`, output `adddup2`, then unconditional `addclose` for all four original pipe numbers (`:891–898`). There is no exclusion for original numbers 0, 1 or 2. The resulting actions are passed to native `posix_spawn` at `:990–992`.

**Concrete counterexample candidate:** Start a valid direct worker with protocol descriptors intact but stderr/fd 2 closed. If the first pipe's read end receives fd 2, the actions first duplicate the stderr write endpoint onto fd 2 (`:894`) and later close `out_pipe[0]`, also fd 2 (`:897`). The close then targets the newly installed child stderr. Closing stdout can produce the analogous collision. A successful spawn alone would not prove that captured stderr was delivered.

**Exact test limits:** The cited `exec_pipes_per_attempt` assertions (`runner_c_worker_harness/run.sh:639–654`) establish 32 clean `/usr/bin/true` spawns under a descriptor ceiling; they do not inspect child stdio or require any output. `runner_exec_inheritance/check.py:57–95` provides an extra descriptor at or above 200, a canary environment, and three fully checked child reports, but launches the harness with open stdout and stderr (`:65–68`). Its child stderr marker assertion (`:89`) is strong for that supplied configuration. It is not a closed-stdio control.

**Retained evidence distinction:** `worker-p4-setup-final/.../controls/worker-collision.json` records a different boundary: host evidence at fd 0 is overwritten before the evidence duplication, and child fd 4 is absent. `issuer-collision.json` records the issuer's high duplicate at fd 64 and preserved fd 3. These agree with the existing prose at `WORKER.md:329–336`; they do not reproduce the exec-child collision. They do demonstrate why requested file actions cannot themselves be treated as endpoint delivery observations.

**What would refute the lead:** A verified invariant that all worker descriptors 0/1/2 are open before every exec attempt, or an actual native observation showing usable stdin/stdout/stderr despite the specific low-number allocation/action sequence. Normal launch inventory alone is not a universal invariant. An unexpected native pipe allocation should be retained and investigated rather than counted as exercising this collision.

**Smallest decisive probe:** In a disposable direct-worker adapter, preserve evidence/policy/readiness delivery, then close only worker fd 2 immediately before the unchanged worker image begins. Run one allow-default exec of an independent observer. Retain the actual pipe numbers/file-action sequence, native spawn result, child fd identities, stdout report, and separate stderr write result. A complementary all-stdio-open run should pass the existing inheritance assertions. Keep the observer's report available through stdout or a separate test-owned channel so missing stderr cannot masquerade as a clean report. No production override or policy change is needed.

**Recommendation:** Run that focused probe before expanding the stdio claim. If confirmed, either qualify the tour and inventory with the demonstrated starting-state limit or harden the descriptor setup and test it. Treat runtime hardening as a separate decision from documentation correction.

## C3 — Two acquisition-period inventory cells put compiler outputs before compilation

**Classification: source-supported; small temporal correction.**

S26a (“Returned compiled profile and its bytecode”) and S26b (“Compiler error string compile_err on failure”) both say `When: Before compilation (compile boundary)` (`docs/architecture.json:7862`, `:7891`). The source initializes `compile_err = NULL` and then acquires the returned profile and error output from `sandbox_compile_string` (`pw_probe_runner.c:1814–1817`), after parameter setup and before optional capture/application. These are compiler outputs, not resources acquired before compilation.

The cited `bare_deny_default` case confirms successful application on its path but neither reports the allocation instant nor exercises the compile-error branch (`run.sh:209–224`). Thus no retained observation independently dates these internal allocations. The source does establish the returned-reference boundary.

**Refutation:** An explicit inventory definition saying “before compilation” includes returned compiler outputs would explain the terminology, but would conflict with the tour's stated use of acquisition periods for call-site placement. **Recommendation:** Use “during compilation; returned before capture/apply” or similarly precise wording. No execution is needed; a native allocation-timing claim would require a separate probe and should not be implied by this correction.
