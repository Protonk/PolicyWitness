Recursive removal may delete `PW_WORK/session.json` and saved output files before encountering a later interruption. A subsequent cleanup unconditionally reads that durable file at line 143 and revalidates every output at lines 151–152; either may already be gone. The existing BYOXPC helper instead keeps its durable file until the end (`session.py` current lines 336–345). The author independently identified this defect and agrees with the correction.

2. **Validate the complete ownership chain before writes or removal.** Outer cleanup first validates the artifact receipt through `workspace(state)`, then reads `work/session.json` and replaces `state` after checking only `workspace_identity` (lines 142–145). A durable record with the same identity but a foreign `state_path` reaches `persist_state` writes; changed `workspace`, `source_app`, `contract`, or `receipt_path` are also trusted without an ownership join. Require regular nonsymlink receipt/durable files, validate the durable owner's paths, and compare the immutable ownership core before adopting its mutable progress. Legitimately newer invocation/cleanup progress may exist in the durable file because `persist_state` writes it before its artifact copy. Do not require the entire two JSON objects to be byte-identical.

   The nested external owner needs the same join: line 155 currently passes any `artifacts/byoxpc-session.json` to the shared cleanup helper. That helper can establish ownership of its own recorded workspace, but the outer owner does not establish that it is *this* workflow's stage. Record the planned external stage/path/device/inode in the outer durable owner before copy/sign/install; join the nested owner to that record before removal. A different otherwise-valid guide session must be refused. If the auxiliary artifact receipt is absent, use only the exact recorded durable path for recovery, preserving the durable-before-artifact persistence order.

3. **Bind the guide layout to the default registry.** The new `session.owned_bundle` guide branch checks the workspace/stage/service/plist but accepts `registry_path` values other than `None`. Common `session.cleanup` then uses that value as a registry override and, for a non-None path, may delete an empty registry directory after its generic basename/service checks. The guide workflow promises default-registry scope and constructs only `None`. Make that restriction part of the guide-layout ownership predicate, before registry inspection or cleanup. Ordinary BYOXPC sessions retain their existing private-registry behavior.

4. **Use an accepted positive control name deterministically.** `controls()` uses `tempfile.TemporaryDirectory(prefix='pw-guide.', dir='/private/tmp')`; its suffix may contain `_`, while `workspace` and the guide branch require `[A-Za-z0-9]+`. The installed Python 3.14 `tempfile.py:134–142` explicitly uses `abcdefghijklmnopqrstuvwxyz0123456789_`. This can randomly refuse the intended positive owner before any negative control. Construct an owned fixture name satisfying the actual layout; do not broaden the ownership predicate merely to accommodate the fixture.

5. **Refuse reuse of an existing top-level owner before preparing another work directory.** `own_work()` replaces `artifacts/session.json` without a preexisting-owner check. The canonical dispatcher normally supplies controlled output ownership, but the new script also exposes run/cleanup entrypoints and must preserve its own interrupted recovery record. Put the check before `prepare-work`, and test that a repeated run leaves the original owner unchanged and issues no command. The author independently proposed this correction.

6. **Join the observed runner to the chosen installation explicitly.** The current status/plist/request checks select the intended service, but verify success checks only outcome/PID and the service-selected create checks only ordinary result/effect fields. Add exact `verify.data.runner_id` and `service_name` equality with the installation record, and bind the returned runner `bundle_id` to `SERVICE`. The implementation populates those verify fields from the selected record (`controller/src/runner_commands.rs:645–653`); native host replies carry the bundle identifier. This makes a successful effect establish the intended runner choice as well as request completion. The author independently proposed these assertions.

## Precision and limits

`safe_disposition` validates an entire `run` envelope, but for `runner_verify` it validates the inner `runner_result` with the independent consumer, then reads the outer report for worker reap. `external()` additionally checks the verify envelope's contract/kind/result/PID. The private REVIEW phrase “every submitted run's full envelope” should describe those actual reader roles, especially while cleanup may be reached before the later success assertions. The current independent consumer is designed around run envelopes; do not broaden its role merely to make that phrase true.

The native recipe requires positive capture, expected signing equipment, a GUI launchd domain and an empty default registry. A native failure may be an equipment/signing/sandbox interruption rather than a guide disagreement; preserve the exact bytes and rerun only under the repository's authorized environment procedure. This review establishes no native success, absence frequency, crash-frequency guarantee, or final release acceptance.
