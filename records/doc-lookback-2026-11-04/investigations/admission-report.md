## Findings

**Public actor execution is implemented, and retained public observations contradict the internal-only account.** The decoder admits `actors`, makes it exclusive with nonnull `policy`, `probe_plan` and `extensions`, and requires phases. The service decodes, checks capacities, checks meaning, and calls orchestration. Orchestration checks those gates again and dispatches actor requests to `runActors`; it dispatches legacy requests through the single-worker path. This is executable control flow, not evidence inferred from examples or comments. Sources: [request decode](../../../runner/Sources/PWRunnerCore/PWRunnerRequest.swift:119), [service gates](../../../runner/Sources/PWRunnerCore/PWRunnerService.swift:303), [driver branch](../../../runner/Sources/PWRunnerCore/CWorkerOrchestrator.swift:64). The stale decoder comment about future wiring does not describe the following code.

Thus A-F1 and W-F1, and L-Q1's `phase_records` statement, are confirmed documentation problems: ARCHITECTURE 166–178 and WORKER 419–422 cannot claim that only the single-worker driver is publicly reached. **The eight-phase and one-consume rules select the legacy form.** `phase_count=8` is enforced only after the actor branch in `admissionFailure`; `actor_phases=16` is a specimen-wide total, including empty visits. An ordinary `probe_plan` becomes one `main` phase. Both forms share the aggregate 256-action limit, counting an ordinary query/attempt pair once and each lifecycle action once. An actor does not acquire another 256 actions or sixteen phases. The 1,024 parameter and 262,143 source-byte limits apply separately to each supplied actor policy; there is no additional aggregate parameter/source cap in these gates. Sources: [capacity routing](../../../runner/Sources/PWRunnerCore/CWorkerRequestPlanning.swift:12), [actor capacities](../../../runner/Sources/PWRunnerCore/ActorPlan.swift:272).

Legacy declaration/consume/release limits are each one, but enforcement differs. Excess declarations use numeric capacity refusal. A second legacy consume or release is a meaning failure (`repeated_consume` / `repeated_release`), not a numeric capacity record. Actor counts are 32 issues and 64 transfers, consumes and releases across the specimen. Repeated consumption of one delivery is legal with distinct handles. At most one release per handle makes 64 releases an implied maximum for a meaningful plan already limited to 64 handles; the separate release count still participates in pre-meaning refusal precedence. No isolated valid-meaning 65-release case exists. L-Q2 is confirmed scope ambiguity, not evidence that values need changing.

**Declaration issuance and actor issuance have different dependency and ordering rules.** The actor dispatch returns before `ExtensionSession` is created. Only a nonempty legacy declaration creates that helper session, before the legacy worker launches. An actor issue is an explicit scheduled action in the issuing actor, after setup; an unapplied actor need not have applied policy. Therefore the blanket pre-worker issuance statement at LIMITS 186 and broad missing-issuer language in ARCHITECTURE need declaration-form qualifiers (A-F5/L-Q3). The actor form's accepted request still capacity-checks a supplied issuer override although its actor runtime does not use it. The historical public corpus includes declaration missing-issuer refusal; absence of a helper in an actor bundle is not independently rerun here. Source branching is sufficient for the runtime dependency distinction, while installation/bundle completeness can impose a separate packaging requirement.

**Exec exclusion is per participating actor, including recipients, and applies to the whole actor plan.** Normalization marks every actor executing a lifecycle action and every transfer recipient as participating. It then rejects any exec in each participating actor, even an exec earlier than that participation. An otherwise separate actor may exec. Legacy nonempty declarations exclude exec in the single worker irrespective of whether the token is consumed. Sources: [normalization and ownership](../../../runner/Sources/PWRunnerCore/ActorPlan.swift:199), [exec exclusion](../../../runner/Sources/PWRunnerCore/ActorPlan.swift:255), [legacy exclusion](../../../runner/Sources/PWRunnerCore/ProbeRunner.swift:193). `lesson-cli-exec_in_extension_actor` retains `extension_exec_unsupported`, empty execution evidence and no file effect; `exec_in_other_actor` is accepted as noted above. This resolves W-F2/M04 without generalizing to arbitrary process authority.

**The published first-failure ordering is incomplete for actors.** Structural decoding precedes capacity checking: schema/types/unknown keys and mixed forms can refuse first. For a structurally decoded request the shared gate checks specimen/run/legacy-format metadata; declaration counts and strings; actor IDs, sandbox-mode and policy-format labels; phase owner IDs and lifecycle-action strings; then override paths. The actor branch next checks actor count, phase count, total action count, phase IDs, issue/transfer/consume/release counts, and each actor policy's source, parameter count and sorted key/value strings. It then checks ordinary slot strings/exec arguments and query fields. Meaning normalization follows, in this order: actor objects/policies, phases/ownership, action structure and ordinary meaning, ordered typed reference lifecycle, per-actor exec exclusion. Legacy ordering is different and remains implemented by its separate path. LIMITS 210–231 and premises 367–390 omit these actor gates (L-Q12).

Each native string first checks UTF-8 size, then NUL; NUL below the byte cap reports `nul_bytes` with maximum zero. Host metadata and ordinary kind/action/filter labels have no NUL capacity rule, though meaning can reject them. Lifecycle operation/family/authority labels do use the 63-byte native-string rule. `admissionRefusalReply` independently sanitizes specimen/run/legacy-format/override metadata and diagnostic step/key echoes regardless of the winning failure; no actor table is echoed by this refusal reply. One nuance for a later implementation review: actor parameter-value admission uses a safely echoed key, but `requestCapacityFailure` maps it to legacy `policy.params.<key>` rather than an actor-indexed path; actor key failures deliberately have no path. This is source-inspected diagnostic imprecision, not a demonstrated unbounded echo.

## Missing-limit search

The search followed decoding, shared capacity admission, both meaning passes, driver selection, policy capture nonce admission, controller actor policy selection, and helper source/import admission. It independently found the following restrictions; M hypotheses were not treated as exhaustive evidence.

- M01: schema 5 is admitted before versioned host fields, closed request objects reject unknown keys, required/optional types are enforced, and plan forms are exclusive. Null optional forms behave as absent. These are grammar restrictions rather than new numeric capacities.
- M02: actor and explicit phase arrays must be nonempty; every declared actor owns at least one phase; phase IDs are nonempty/unique, all action step IDs unique, and actor/lifecycle step IDs nonempty. Empty action arrays are permitted. Legacy ordinary step IDs do not receive the same explicit empty-ID check. Do not publish a blanket nonempty-step claim.
- M03: typed token/delivery/handle names are single-assignment across all three types; each use follows its syntactic producer in global schedule order and obeys producing/receiving/consuming ownership. Self-transfer and repeated consume with distinct handles are allowed. Runtime producer failure does not retroactively make syntax invalid.
- M05: actor issue requires family `file`, authority `read` or `read_write`, and an absolute target; legacy authority defaults to `read`. Closed objects do not accept raw token, native class or flags as arbitrary inputs. These are supported interface capabilities, not assertions that macOS lacks other APIs.
- M11: seven known filter kinds and a finite attempt kind/action mapping are admitted; `args` is exec-only, exec target absolute, `none` filter forbids a supplied value, other filters require nonblank values. Operation names themselves are not a finite admitted set: any nonblank name within its byte/NUL bounds can reach query planning.
- Additional independent restriction: enabled compiled-profile capture requires exactly 32 lowercase hexadecimal nonce bytes, and a nonce without enabled capture is inapplicable. [captureNonceBytes](../../../runner/Sources/PWRunnerCore/CWorker.swift:690) and [policy meaning](../../../runner/Sources/PWRunnerCore/ProbeRunner.swift:64) establish this; it deserves either an explicit admission-limit entry or a clear grammar cross-reference if LIMITS retains an exhaustive promise.
- M16: the helper accepts a separate `{policy: ...}` shape without a request-schema gate; its serde shape does not deny unknown fields. Its source cap is 4 MiB decoded UTF-8 source, excluding imported files and surrounding JSON. It has no counterpart of the runner's parameter count/key/value capacities. NUL in source, parameter key or value is refused before native calls. Import inventory limits do not constrain libsandbox compilation. Source cap exact/over UTF-8 assertions use controlled native calls; depth/count assertions use filesystem import chains. The source count is not a memory allocation bound on initial JSON reading.

Controller fallback selects every actor's object-valued `sandbox.policy` without requiring `sandbox.mode=apply` or admitted actor count. A fallback can occur before host admission, so the eight-actor and runner policy limits cannot be assumed to bound those helper invocations. Sources: `controller/src/run_flow.rs:668–690,412–435`. This fact was sent to the evidence investigator, who owns full fallback output and budget analysis. It prevents misleading extension of admitted-request limits to diagnostic fallback inputs.
