**Finding.** Replacing the absent sibling changed zero allow-side entries for all three operation/filter pairs. Each complete 200-row table also matched its partner on the deny side and on every strict-match flag. Each scan completed through ID 200, found zero strict matches and exited 1. [Row-by-row comparison](calibration/comparison.json) This host supplies no reason to reopen an exclusion.

**What the harness measures.** The script applies an allow-default policy with one filtered deny to a lingering native probe. The probe exercises the denied operand before and after applying the policy. A separate invocation of the shipped validator queries that PID twice for each candidate ID, once with the target string and once with the sibling string. The strict rule accepts the query pattern `deny, allow`. The harness makes no native attempt on the sibling. I set `PW_PYTHON=/opt/homebrew/opt/python@3.14/bin/python3.14` and selected the shipped validator explicitly. ## 2. What happens when a file open cannot return?

**Finding.** On the shipped app, a legitimate read of a FIFO with no writer reached the attempt and remained in `open`. The host timed out, requested termination and confirmed the worker's reap. Ordinary `run` returned in about **121.09 seconds**. The response preserved an unknown operation return and the available prediction.

I created a private directory under `/private/tmp` and a mode-0600 FIFO. `test-input read --target "$W/pipe"` emitted an allow-default `read_fresh` specimen named `test-input` with step `read-target`. The shortened and ordinary runs used identical specimen bytes and the same FIFO, with no writer during either run. A 17-byte regular file was the positive control. The supervisor measured monotonic elapsed time around the CLI, sampled the exact bundle's newly appearing worker and parent, registered a kernel exit event on the live worker, and checked the PID again after return. Its independent 12-second or 145-second deadline could attach a nonblocking writer and supply a byte to this private FIFO. The harness also bounds its CLI wait and has a PID-checked fallback. None fired. Times below include supervisor polling. [Supervisor](methods/observe.py) · [FIFO specimen](blocking/fifo-specimen.json) · [Regular-file specimen](blocking/regular-specimen.json)

The displayed rc −1 came from the synthetic record. The file-operation return remained unknown. The comparison observation was `unavailable`. All three CLI stderr captures were empty. A separate 7-second run of the generated read specimen independently located the wait. All 179 stack samples stopped in `run_attempt → open → __open`. **Termination and reap.** In both main FIFO runs, `poll_stop_reason` was `sentinel_deadline`, `done_observed` was false, the signal-9 request returned zero, final `term_signal` was 9, `reaped` was true and `wait_errors` was empty. These runs establish cleanup for these workers. The signal request alone would have been insufficient evidence.

**Guide and recommendation.** The shipped guide explains synthetic missing results, FIFO byte consumption and the independent client timeout. Add a sentence beside the file actions explaining that a FIFO reader can wait for a writer, a connected reader can wait for data, and a regular file or coordinated peer is appropriate when the caller expects prompt completion. The existing `worker_sentinel_wait` limits row already describes the 120-second allowance and partial evidence. Keep that row and the current blocking semantics. The existing default case `witness_contract/worker_attempt_in_flight_at_deadline` already uses writerless FIFOs, a shortened deadline, observed SIGKILL and reap, and distinct started and unreached steps. A full-duration duplicate would add roughly two minutes with little additional coverage. ## 3. Which environment does the ordinary worker receive?

**Finding.** The historical assertion that an ordinary worker inherits its host's environment is contradicted by the actual launch argument and a controlled native spawn on this host. The observed production worker displayed no environment suffix in `ps -Eww`. That external observation has a narrower meaning than a live enumeration of its C environment.

The frozen guide is a historical Git object. Its revision and digest are pinned in `docs/publication.py`. Lines 2884–2890 distinguish the empty environment of an exec helper, the explicitly empty actor-worker environment and the claimed ordinary-worker inheritance, with no full ordinary-worker snapshot. The replacement v0.3.8 guide omits this inheritance claim. The implementation tour says that the ordinary host supplies nil `envp`, the examined Apple spawn wrapper forwards it, and the examined exec code constructs an empty environment. Its earlier launch inventory observed identical plain and environment-displaying output. [Frozen passage](provenance/frozen-guide.txt) · [Publication source](../../docs/publication.py) · [Worker tour](../../docs/WORKER.md#launch-observation-l)

**Implementation boundary.** Both host routes use `ActorSession`. It passes nil for the ordinary worker and an explicit null-terminated empty array for an actor worker. Inspection of the worker's main, argument decoding, application and attempt path found no call that clears the incoming environment or replaces its vector. Separately, an exec attempt passes its own explicit empty vector to the helper. Supplying a marker to the initiating CLI would provide no control over the environment of the launchd-managed XPC host. The contaminated-worker fixture deliberately supplies its own environment through a test launcher. [Host spawn](../../runner/Sources/PWRunnerCore/ActorSession.swift) · [Worker main and hold](../../controller/tools/pw_probe_runner/pw_probe_runner.c) · [Exec child spawn](../../controller/tools/pw_probe_runner/pw_worker_exec.h) · [Contaminated-launch controls](../../tests/suites/runner_exec_inheritance/README.md)

**Runtime controls.** A local hardened-runtime C control started with just `PW_FINDINGS_CANARY=visible_1124`. It used Darwin `posix_spawn` to start a child with the chosen environment argument. The child counted its own C environment and tested the marker at entry, applied allow-default, optionally cleared the marker, reported again, and waited on a pipe. I ran the same plain and `-Eww` ps commands against the reported PID only after the child signalled this point. No unrelated environment values were saved. For the shipped ordinary worker, I submitted a generated regular-file read with `test-input run --worker-post-apply-hang-ms 20000`. The selected hold is after application and slot execution and before terminal publication. Both ps commands succeeded against PID 60494 and returned the same 81 bytes of worker argv. The argv identified the requested hold. The matching response reported a completed read, finished execution and reap. PID, parent, elapsed time and subsequent exit were recorded separately. This was external sampling during the selected window. There was no in-process environment census of the production worker. **Recommendation.** Retire the frozen guide's ordinary-inheritance sentence as a source for future documentation. The current shipped guide already omits it. Keep the worker tour's source-scoped account, explicitly distinguish the two spawn arguments where it says “the host passes nil envp”, and qualify the ps observation as display evidence. Correct the nearby `ActorSession.swift` comment about inherited ordinary-worker environment when that commentary is next edited. No worker initialization change is indicated.

## 4. Does the default battery detect removal of the one-byte read?

**Finding.** Fixture compilation detected the literal deletion through its unused variable. Removing that variable as well allowed the missing read to survive the complete default battery. A caller sampling a preloaded FIFO distinguished both variants from the original after successful, published opens.

**Reason for the mutation.** After a successful read-only open, `attempt_file_open_read` captures the descriptor path, tries a one-byte read, closes and reports open success. It discards the read and close returns. Decision 14 preserved the call because an existing specimen can consume a byte from a stream. A plain open/close leaves a queued byte available, while ordinary regular-file contents can look identical either way. The earlier FIFO control and decision were removed from the working tree during guide closeout and remain in Git at v0.3.8. The current guide describes the one-byte attempt and the public probe surface explicitly specifies it after a successful open. **Build control.** I built the original from a clean detached worktree and deleted exactly `(void)read(fd, &b, 1);` in a second worktree at the same revision. **Recommendation.** Add a small queued-byte row to the existing file-effects coverage when test changes are in scope. Decision 14 and the shipped guide give the distinction operator-visible compatibility significance. The connected-empty control is valuable diagnostic evidence but does not need to add its timeout to the default battery.
