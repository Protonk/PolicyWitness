The initial scheduling choice is to keep implementation and native execution
in the main checkout. D1 may run after C0 on an isolated fixed checkout while
E1/E2 proceed, provided its inputs and evidence are protected. D2 consumes D1
in order and refreshes relevant facts after intervening changes; its executable
changes are serialized with refactor changes to shared machinery. C and Swift
refactors run sequentially unless their actual design establishes an isolated
boundary. Separate commits distinguish apparatus improvements from adaptations
required by a refactor.

## Verification choices

Use the public dispatcher and fresh `tests/out/runs/workset-*` directories.
Inspect selections before execution. The original app is v0.3.3, build 853;
its production source files match the intake tree, but that alone supplies no
new runtime verification. Build a matching signed candidate for production
changes and retain source/build identities separately from acceptance commits.

E1 starts with `sandbox_extensions_native/feasibility` and its native fixture.
Any added scenarios or cases use the existing dispatcher and receipt ownership.
Public extension changes require the affected `witness_contract` extension,
phase and combination cases, independent consumer controls, and coordinated
admission/transport suites in `tests/AGENTS.md`. Include the applicable BYOXPC
extension/signing witness; native feasibility alone cannot establish its path.

R1 and R2 inherit their named plans' verification requirements. Select exact
additional controls against the completed designs. In particular, relocation
must not disconnect native interception, source membership, mutation anchors,
or client shared-source compilation. Include order-barrier mutations when its
specified implementation or observer triggers are touched, and the native
clock control when its change/applicability conditions apply.

D1 uses committed historical trees for replay facts and labels supplied
annotations and designer exposure. D2 checks each supported executable change
with independent accepted and rejected controls; prose-only work does not
justify a full live battery by itself. Final verification reconciles changed
dependencies across both work streams rather than adding their passing counts.

## Resources and interruption

The main checkout has one execution/build lock. Do not run competing builds or
tests there. Sub-agent assignments name their checkpoint, source state, allowed
writes and stopping boundary; reconcile them before their stage seal. Isolated
worktrees still share host services and keychain equipment, so arrange exclusive
ownership for live operations where needed.

Keep the existing pytest-evidence worktree and release archives untouched.
Inspect existing drift receipts before selecting reusable cost evidence; pin
any such run before pruning. Current raw runs are local and gitignored. Routine
pruning uses the supported preview/apply commands after active evidence is
protected. No release, upload or publication is needed for this workset.

On interruption, stop dispatching, use the running operation's cancellation and
cleanup path, and update the checkpoint with command/session identity, completed
and partial evidence, owned resources and next work. Missing completion remains
missing. Findings that reconsider existing promises and proposals to omit a
required refactor go to the user with evidence; independent work may continue.
